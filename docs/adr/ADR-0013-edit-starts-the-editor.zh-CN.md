# ADR-0013：edit 启动设置里写的编辑器

## 1. 状态

已接受。Troy 于 2026-11-21 接受了这个决定，即 F16 设计里 C 点的做法 1。

## 2. 背景

`recipe-menu edit ID` 用设置里写的编辑器（默认是记事本）打开菜谱文件，等你关闭编辑器，然后检查这个菜谱（需求 4，F16）。所以工具必须启动另一个程序并等它结束。ADR-0001 本来就写明 v0.2 用 `subprocess` 启动编辑器。

架构 4 说只有 `cli` 接触外部世界，架构 8 列出只有 `cli` 读取的内容，其中包括环境变量。`cli` 通过 `Context` 和 `main` 的参数把它们传下去，所以测试可以给出固定的值（ADR-0003）。这两节都没有讲启动另一个程序。

启动编辑器会以三种方式接触外部世界，而架构 4 和 8 把这些留给 `cli`：

- 为了找到编辑器，`shutil.which` 从进程的环境里读取 `PATH`，在 Windows 上还读取 `PATHEXT` 和 `NoDefaultCurrentDirectoryInExePath`。在 Windows 上，除非设置了最后这个变量，它会先在当前文件夹里找。
- 编辑器拿到 `recipe-menu` 的环境、当前文件夹和控制台，就像你在 PowerShell 里输入它的名字一样。
- 所以 `main(environ={})` 能让其他命令都避开进程的环境，却不能让 `edit` 避开进程的 `PATH` 和当前文件夹。

在 Windows 上，Python 等待进程时不会因为 Ctrl+C 醒来，所以直接等待会把 Ctrl+C 一直压到编辑器结束。

## 3. 决定

- `edit` 用 `shutil.which` 找到程序，即设置 `editor` 的第一个词。它用 `subprocess.Popen` 启动 `[找到的程序, *选项, 菜谱文件的完整路径]`，不用 shell，不传 `env`、`cwd` 和流，并在循环里用 `Popen.wait(timeout=0.5)` 等它结束（F16 设计，选择 4 和 5）。
- 只有 `edit` 启动程序，而且只启动设置里写的编辑器。其他模块都不启动程序，也不调用 `shutil.which`。架构 4 和 8 写明这是“只有 `cli` 接触外部世界”这条规则唯一的例外。
- `edit` 只在启动编辑器的函数里引用 `subprocess` 和 `shutil`，并以 `subprocess.Popen` 和 `shutil.which` 的写法调用它们，所以其他命令不会加载它们，测试也能通过 `monkeypatch` 替换其中任何一个。
- 编辑器找不到、启动不了，或者以 0 以外的退出码结束，都不是数据里的错误。`edit` 在错误流上写一行，返回 1。它只捕获 `Popen` 的 `OSError`，以及它每一步等待抛出的 `subprocess.TimeoutExpired`，后者只表示编辑器还在运行。等待时按 Ctrl+C，会交给 `cli`，退出码为 130，编辑器继续运行。架构 6 为此有一行。
- 测试都不启动真正的编辑器。运行 `edit` 的测试设置 `edit` 搜索的 `PATH`，只让它找到一个不开窗口的替身编辑器（架构 10）。
- 工具仍然从不使用网络。编辑器是你自己选的程序，不属于这个工具，所以它可以用网络，VS Code 就会用。

## 4. 考虑过的方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 做法 1：`edit` 自己用 `subprocess.Popen` 启动编辑器，先由 `shutil.which` 在 `PATH` 上找到它，编辑器拿到 `recipe-menu` 的环境、当前文件夹和控制台。已选。 | 一个命令启动需求点名的一个程序，所以一条范围很窄的规则就够了。`Context` 和 `main` 的字段和参数都不变，所以 F15-T03 仍然成立，mock PR 之前不需要测试修正 PR。`app` 里不会多出启动程序的接口。编辑器的启动方式和你在 PowerShell 里输入它的名字一样，所以 `code` 能找到 `code.cmd`。 | 架构 4 和 8 多了一个例外，`main(environ={})` 也不再能让 `edit` 避开进程的 `PATH` 和当前文件夹。设计没有列出的两个缺点：运行 `edit` 的每个测试都需要一个守卫来管它的 `PATH` 和当前文件夹，因为在 Troy 的电脑上，一个既没写键 `editor`、又没有守卫的测试会启动真正的记事本，并一直等到有人把它关掉。而且测试每运行一次 `edit` 就启动一个真正的进程，即一个 Python 写的替身，所以这些测试比留在测试进程里的测试慢。 |
| 做法 2：由 `cli` 替命令启动程序。`Context` 多一个字段，即一个启动程序并等它结束的函数，由 `main` 填入，测试在进程里把它换成替身。`edit` 调用它。 | 架构 8 的规则保持完整：`main` 会在它的 `environ` 的 `PATH` 里找程序，所以 `main(environ={})` 仍能让每个命令都避开进程的环境。`edit` 的测试不会启动进程，只有 `cli` 里启动函数的测试会。 | 只有一个命令用的字段进入了每个命令的上下文，启动程序的接口也进入了 `app`。比较 `Context` 字段名称的 F15-T03 要在 mock PR 之前的测试修正 PR 里修改，架构 5.2 里 `Context` 一行也要改。设计的选择 4、5、9 和 10、第 3 节及示例都要在 mock PR 之前修改。它仍然需要一份 ADR 来改架构 5.2 和 8，真正启动程序的那个测试仍然需要替身。 |

## 5. 影响

- 架构 4 和 8 在 5.2 版写明这条规则。架构 6 多了命令启动的程序这一行，架构 10 写明测试都不启动真正的编辑器。架构 5.2 里 `Context` 一行和 `main` 的参数都不变。
- ADR-0003 保持 Troy 接受时的样子。它的“只有 `cli` 读取环境”这条规则对其他每个模块都成立，对 `edit` 除了查找编辑器之外的每次读取也都成立。`subprocess`、`shutil` 和 `time` 都是标准库模块（ADR-0001），所以 R16 没有要审查的东西。
- F16 的设计和测试计划保持 Troy 在 1.0 版批准的样子。设计的选择 4、5、9 和 10，以及测试计划里的守卫、替身和用来观察或抛出异常的 `Popen`，本来就按做法 1。不改任何需求、原型或场景，之前功能的测试和代码也都不变。
- 其他命令启动时不加载 `subprocess` 和 `shutil`，按设计评审的测量，在 Troy 的电脑上这样每次能省下大约 11 到 15 毫秒。ruff 会在启动编辑器的代码上报出 `S603` 和 `PLC0415`，这些行各带一个写明理由的 `noqa` 注释（F16 设计，选择 4）。
- 在 Windows 上，除非设置了 `NoDefaultCurrentDirectoryInExePath`，你运行 `edit` 的文件夹里如果有和编辑器同名的程序，它会代替 `PATH` 上的那个运行。Troy 的终端没有设置这个变量。
- 批处理形式的编辑器（比如 `code.cmd`）经 `cmd.exe` 拿到参数。数据文件夹的路径里有 `%`，或者路径里有 `&`、`|`、`<`、`>`、`^` 而没有空格时，编辑器拿到的路径会被改动，而且 `&` 后面的路径部分可能被当作命令运行（设计评审，备注 6）。设计只写到了 `%NAME%`。ID 里从不会有这些字符，数据文件夹由你自己选，Troy 电脑上默认的数据文件夹里也没有这些字符。`.exe` 形式的编辑器（比如记事本）拿到的每个参数都和写的一样。
- `Popen` 失败时，提示里的原因是系统自己的文字，使用系统的语言，在 Windows 上可能带有字面的 `%1`（设计评审，备注 2）。
- 架构 1 的“不用网络”和架构 7 的规则讲的都是这个工具。编辑器做什么由它自己决定，比如 Windows 11 的记事本可能把打开的标签页里的文字（包括没保存的）存起来，以便以后恢复。
- 以后的命令如果要启动程序，或者别的模块要用 `shutil.which`，都需要另外修改架构 8，并写一份 ADR。规则变更流程可以用 ruff 的禁用 API 规则 `TID251` 把这条规则变成代码检查：在 `edit` 以外的地方禁用 `subprocess`、`shutil.which`、`os.system`、`os.startfile`、`os.popen`，以及 `os.exec` 和 `os.spawn` 系列函数。
