# ADR-0002：TOML 数据文件，用 tomllib 读取

## 1. 状态

已接受。Troy 于 2026-11-10 批准 `docs/architecture.md`，接受了这条记录。

## 2. 背景

需求第 3 节把数据文件的格式交给架构决定，原型里用的是 TOML。Troy 用记事本或 VS Code 手写这些文件，中英文都有。语法错误必须给出行号，值错误必须给出字段。工具绝不能改动 Troy 写的文件，只有 v0.2 的 `menu suggest` 会填充菜单里空的餐。`check`、`list` 和 `search` 最多要读 1,000 个菜谱文件，并且必须在 1 秒内结束（PT01）。

## 3. 决定

- 每个数据文件都是 TOML 1.0，格式与 `docs/prototypes/example-data.md` 相同，扩展名为 `.toml`。总体架构第 5.1 节列出这些文件。
- `datafile` 以字节读取文件，按 UTF-8 解码（带不带字节顺序标记都可以），再用 `tomllib` 解析。语法错误给出行号：Python 有 `tomllib.TOMLDecodeError` 的 `lineno` 属性时（3.14）取这个属性，在 Python 3.13 上取错误信息末尾的 “(at line N, column M)”。遇到超过 4,300 位的十进制整数时，`tomllib` 抛出普通的 `ValueError`；遇到嵌套太深时，抛出 `RecursionError`。`datafile` 也捕获这两个异常，把每一个都变成带行号的 `Problem`（F03 设计 2.3）。
- 值错误写出字段，比如“食材 3”，因为 `tomllib` 不给出值的位置。这正是需求第 3 节的要求。
- 创建文件的命令写出代码按模板生成的文本。工具没有 TOML 写入器。
- v0.2 的 `menu suggest` 怎么修改已有的菜单文件，在 F14 的设计里决定。它要么只改写空餐所在的行，要么使用能保留文件排版的库（比如 tomlkit），而后者是 R16 下的新依赖。

## 4. 考虑过的方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| TOML，用 `tomllib` 读取 | 在标准库里。支持注释和 Unicode 字符串，缩进没有含义。原型和 `init` 的文件已经在用它。语法错误带有行号。 | 标准库里没有写入器。纯 Python 解析。值不带位置。 |
| YAML | 写起来短，列表好读。 | 需要 PyYAML 这个依赖。在记事本里很容易写错缩进，单独一个 `no` 会变成 false。 |
| JSON | 在标准库里，解析快。 | 没有注释。到处都是引号和逗号，很难手写。 |
| 自己定义的行格式 | 可能是最短的写法。 | 需要自己的解析器、两种语言的语法错误提示和文档。Troy 还得多学一种格式。 |

## 5. 影响

- `init` 写出的文件和原型完全相同，任何编辑器都能打开。
- 解析所有菜谱是 `list`、`search` 和 `check` 最大的开销。在 Troy 的电脑上第一次测量 PT01（F07 或 F09 的 PR 5）时，就能看出还剩多少余量。
- 如果 PT01 不达标，缓存解析过的菜谱就要写一个 v0.1 不允许写的文件（“你的文件保持你写的样子”），所以要先改需求，再改总体架构。
- 在 F14 的设计里修改已有文件要小心，因为整个重写文件会丢掉 Troy 的注释。
