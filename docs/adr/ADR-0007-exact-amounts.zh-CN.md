# ADR-0007：用分数表示精确的数量

## 1. 状态

已接受。Troy 于 2026-11-10 批准 `docs/architecture.md`，接受了这条记录。

## 2. 背景

购物清单把每道菜按它的份数除以菜谱的份数来缩放，把斤、两、tsp 和 tbsp 换算成克和毫升，把结果加起来，再把计数、克和毫升向上取整（需求 3，Q18）。向上取整会暴露每一个微小的误差：在二进制浮点数里，0.1 × 3 等于 0.30000000000000004，所以本该正好是 450 g 的总和可能多出一丝，被向上取整成 451 g。菜谱里也可能写小数，比如“1.5 kg”。

## 3. 决定

每个数量都是 `fractions.Fraction`。`units` 把“1.5”读成精确的 3/2。缩放、换算和相加都保持精确，向上取整对精确值使用 `math.ceil`。`units` 只在写出数量时才把它变成文字，最多两位小数。整个工具里没有任何 `float` 存放数量。

## 4. 考虑过的方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| `fractions.Fraction` | 对每个缩放系数（比如 4/3）和每种单位换算都精确。向上取整总是对的。 | 比 `float` 慢，但对几百行的清单没有影响。 |
| `decimal.Decimal` | 对小数形式的数量精确。 | 4/3 这样的缩放系数不精确，所以总和可能刚好超出一个整数一点，被多向上取整一个单位。 |
| `float`，向上取整前留一个很小的容差 | 快，大家都熟悉。 | 容差是猜的。猜错了就会多出一克或一个。 |
| 用毫克和微升的整数 | 单位换算精确。 | 按 4/3 缩放仍然不精确，计数还得另想办法。 |

## 5. 影响

- F13 原型里的购物清单正好按它的表格相加，比如 菜心 500 g + 500 g × 2 = 1.5 kg。
- 总体架构第 8 节禁止用 `float` 表示数量，代码审查会检查这一点。
- 测试把数量当作精确值比较，不留容差。
