# F12 Build the shopping list: test plan

## 1. Feature

- ID and name: F12 Build the shopping list
- Design: [design.md](design.md), version 1.0

## 2. Cases

The tests call the five interfaces of `recipe_menu.shopping`: `ShoppingLine`, `ShoppingLine.amount_text`, `ShoppingGroup`, `ShoppingList`, and `build_shopping_list`. F12 has no command, so the plan has no functional cases. A unit case calls an interface with values that it builds in code. F03, F04, and F06 let a test build a `Catalog`, a `Recipe`, and a `WeekMenu` with no file. An integration case reads a fresh copy of `tests/data/example/` with the readers of F03 to F06, checks a prototype or a v0.1 scenario, or builds random weeks. Each case names the part of the design that it comes from, such as (choice 4). The design's five examples and their 22 `# raises` lines are in F12-T01 (2.1), F12-T05 (2.2), F12-T08 (2.3), F12-T11 (2.4), and F12-T14 (2.5).

**R09.** The mock holds `shopping/__init__.py` with the four names, and two internal files. They define the three values with their fields and doc comments, without the checks of their constructors, and `build_shopping_list`. Its `amount_text` and its `build_shopping_list` raise `NotImplementedError` (design section 2). So a test passes against the mock when it checks only the four names, or only the fields, the equality, the hash, or the frozenness of a valid value, such as `ShoppingList(IsoWeek(2026, 46), 0, 0, (), ())`. Each case that checks such a thing also checks something that the mock gets wrong: a `TypeError` or a `ValueError` from a constructor, a text from `amount_text`, or a list from `build_shopping_list`. F12-T02, F12-T10, and F12-T13 check valid values only beside such a result. A case that expects an error names `ValueError` or `TypeError` in `pytest.raises`, never `Exception`, because the mock raises `NotImplementedError`, which is neither. `tests/f12_support.py` builds every value in its functions, so importing it calls no interface of F12.

**Both systems.** F12 touches no path, no clock, and no stream. The integration cases read copies in `tmp_path` through the readers of F03 to F06, whose tests pass on both systems. So every case runs on Windows and on Linux, and no case is skipped on either.

**Tests of earlier features.** F12 changes no interface of F01 to F11 (design section 3), no test of an earlier feature, and no file of `tests/data/example/`.

**The prototype and the scenarios.** F12 gives the values of the list and the text of each line's amounts, and F13 prints them. So F12-T29 to F12-T32 check the list, the names of its categories and ingredients, and `amount_text` in both languages, for the F13 prototype's table "How the example adds up" and its two outputs, and for v0.1-S14, v0.1-S16, and v0.1-S18. The printed layout, the count line, the pantry line's text, the "Saved" line, and the saved file are F13's (section 4).

These conventions hold in every case:

- `600 G` stands for `Quantity(Fraction(600), Unit.G)`, and `3/2 STALK` for `Quantity(Fraction(3, 2), Unit.STALK)`, as `q` of `tests/f01_support.py` builds them. `1/10**16 G` is `Quantity(Fraction(1, 10**16), Unit.G)`. `TO_TASTE` is F01's.
- "The code catalog" is the catalog that the example of 2.5 builds in code: the six categories and the 22 ingredients of `tests/data/example/catalog.toml`, in its order, and no tags. "The code pantry" is the pantry of that example: 食用油, 盐, 糖, 生抽, and 花椒. "No pantry" is `Pantry(frozenset())`. "The code recipes" are the eight recipes of that example: the seven of the example folder and `scallion-noodles`, each with 2 servings, as a `dict` in the example's order.
- In a case, a Chinese name in code font, such as `番茄`, is the ingredient of that name in the case's catalog, as `catalog.find_ingredient("番茄")` gives it. A category key, such as `produce`, is the catalog's category with that key.
- `R(three, 3: 番茄 100 g, 鸡蛋 1)` is the recipe that `recipe` of `tests/f12_support.py` builds, as the example of 2.5 does: `Recipe("three", BiText("three"), 3, (), lines, Steps(("Cook.",)))`. Each line is the ingredient of the Chinese name and the quantity that `parse_quantity` reads from the rest of the text with the ingredient's default unit. `R(r1: ...)`, with no number, has 2 servings. A case's mapping is a `dict` from each recipe's ID to the recipe.
- A dish is written as its recipe ID and its servings, so `tomato-egg 2` is `Dish("tomato-egg", 2)`. A menu is its week, its meals, and its slots with dishes, such as "Monday dinner: `r1 2` and `r2 2`". `make_menu` of `tests/f06_support.py` builds it, and every other slot holds no dish. Unless a case says otherwise, the week is 2026-W48, the meals are lunch and dinner, the catalog is the code catalog, and the pantry is no pantry.
- `build` stands for `build_shopping_list(menu, mapping, catalog, pantry)`.
- `番茄: 600 G` stands for `ShoppingLine(番茄, (600 G,))`, `葱: 5 STALK, 1 BUNCH` for `ShoppingLine(葱, (5 STALK, 1 BUNCH))`, and `白胡椒粉: ()` for `ShoppingLine(白胡椒粉, ())`. `produce [番茄: 600 G, 葱: 5 STALK]` stands for `ShoppingGroup(produce, (番茄: 600 G, 葱: 5 STALK))`. Inside a group, each line starts at an ingredient's name and its colon, and the amounts after the colon belong to that line.
- `List(2026-W48, 1, 2, [g1, g2], [食用油, 盐])` stands for `ShoppingList(IsoWeek(2026, 48), 1, 2, (g1, g2), (食用油, 盐))`. An expected list is compared with the result by `==`.
- EN and ZH are `Lang.EN` and `Lang.ZH`. "Texts EN: a and b" means that `amount_text(Lang.EN)` of the lines, in the order of the groups and of their lines, gives `"a"` and `"b"`.
- "An equal but separate copy" of a `Category` or an `Ingredient` is a new object built from equal fields, so it is `==` to the original and not the same object.
- F12-T07, F12-T28, and F12-T33 use the fixture `default_int_limit` of `tests/conftest.py`, which sets Python's limit on `int` digits to its default of 4,300 for the test. Design 2.2 and choice 10 state the limit for that default.

The helpers of `tests/f12_support.py` are these:

- `code_catalog()` gives the code catalog. `code_pantry(catalog, names)` gives the pantry of the ingredients with those Chinese names, and gives the code pantry when `names` is left out.
- `recipe(catalog, recipe_id, lines, servings=2)` builds `R`. `code_recipes(catalog)` gives the code recipes.
- `line(catalog, name, *amounts)` and `group(catalog, key, *lines)` build a `ShoppingLine` and a `ShoppingGroup` of the catalog's items for an expected list. `expected_w47(catalog)`, `expected_s16(catalog)`, and `expected_s18(catalog)` give the expected lists of F12-T29, F12-T30, and F12-T31 with the items of a catalog.
- `written(shopping, lang)` writes each group's `category.name.get(lang)`, and each line as `- `, the ingredient's `name.get(lang)`, a space, and `amount_text(lang)`, as the example of 2.5 does.
- `read_week(folder, week)` reads the files that F13's `shop` will read (design section 2): `read_settings`, `list_recipe_ids`, `read_week_menu` with the settings and the IDs, `read_catalog`, `read_pantry` with the catalog, and `read_recipe` once for each ID that a dish names, into a `dict` in the order in which the dishes first name them. It checks that each reader gives its value and no error, and gives the menu, the mapping, the catalog, and the pantry.
- `s16_folder(example, target)` and `s18_changes(folder)` write the files of v0.1-S16 and v0.1-S18 (F12-T30 and F12-T31).

## 3. Performance cases

None. No interface of F12 has a performance target (design 2.1 to 2.5, choice 11), and R14 gives performance tests only to interfaces that have one. PT01 times F13's `shop` from start to exit on Troy's PC (v0.1-S32). `shop` calls `build_shopping_list` once, so F13's performance case for `shop` will time this call as part of the command.

The plan leaves the timing to F13 for that reason. The Architect's model took a median of 5.1 ms for `build_shopping_list` on the PT01 week 2026-W26 of `tests/pt01_support.py`, and 1.9 ms for `amount_text` of its 290 lines in both languages (design section 4). That is less than 1% of PT01's second, and a timed case of the function alone would have no target to fail. F12-T23 and F12-T28 build weeks of 21 meals and 63 dishes, the most dishes that a PT01 week holds, without timing them.
