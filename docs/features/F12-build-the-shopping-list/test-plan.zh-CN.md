# F12 生成购物清单：测试方案

## 1. 功能

- 编号和名称：F12 生成购物清单
- 设计：[design.zh-CN.md](design.zh-CN.md)，版本 1.0

## 2. 用例

测试调用 `recipe_menu.shopping` 的五个接口：`ShoppingLine`、`ShoppingLine.amount_text`、`ShoppingGroup`、`ShoppingList` 和 `build_shopping_list`。F12 没有命令，所以方案里没有功能用例。单元用例用它在代码里构建的值调用一个接口。F03、F04 和 F06 让测试不用文件就能构建 `Catalog`、`Recipe` 和 `WeekMenu`。集成用例用 F03 到 F06 的读取函数读取 `tests/data/example/` 的新副本，检查一个原型或一个 v0.1 场景，或者构建随机的星期。每个用例在括号里注明它来自设计的哪一部分，比如（选择 4）。设计的五个示例和其中 22 行 `# raises` 分别在 F12-T01（2.1）、F12-T05（2.2）、F12-T08（2.3）、F12-T11（2.4）和 F12-T14（2.5）里。

**R09。** mock 里有带四个名称的 `shopping/__init__.py`，以及两个内部文件。它们定义三个值（带字段和文档注释，没有构造函数的检查）和 `build_shopping_list`。它的 `amount_text` 和 `build_shopping_list` 抛出 `NotImplementedError`（设计第 2 节）。所以一个测试如果只检查四个名称，或者只检查一个有效值的字段、相等性、哈希或不可变性，比如 `ShoppingList(IsoWeek(2026, 46), 0, 0, (), ())`，它对着 mock 会通过。检查这类内容的每个用例，也检查 mock 做错的东西：构造函数抛出的 `TypeError` 或 `ValueError`、`amount_text` 给出的文字，或者 `build_shopping_list` 给出的清单。F12-T02、F12-T10 和 F12-T13 只在这样的结果旁边检查有效值。预期出错的用例在 `pytest.raises` 里写明 `ValueError` 或 `TypeError`，从不写 `Exception`，因为 mock 抛出的 `NotImplementedError` 两者都不是。`tests/f12_support.py` 在函数里构建所有值，所以引用它不会调用 F12 的任何接口。

**两个系统。** F12 不涉及路径、时钟和数据流。集成用例通过 F03 到 F06 的读取函数读取 `tmp_path` 里的副本，这些读取函数的测试在两个系统上都通过。所以每个用例都在 Windows 和 Linux 上运行，没有用例在任何一个系统上跳过。

**之前功能的测试。** F12 不改 F01 到 F11 的任何接口（设计第 3 节），不改之前功能的任何测试，也不改 `tests/data/example/` 的任何文件。

**原型和场景。** F12 给出清单的值和每一行数量的文字，由 F13 打印出来。所以 F12-T29 到 F12-T32 针对 F13 原型的表格“How the example adds up”和它的两段输出，以及 v0.1-S14、v0.1-S16 和 v0.1-S18，检查清单、其中分类和食材的名称，以及两种语言的 `amount_text`。打印的排版、计数行、常备行的文字、“已保存”那一行和保存的文件都归 F13（第 4 节）。

以下约定适用于每个用例：

- `600 G` 代表 `Quantity(Fraction(600), Unit.G)`，`3/2 STALK` 代表 `Quantity(Fraction(3, 2), Unit.STALK)`，与 `tests/f01_support.py` 的 `q` 构建的一样。`1/10**16 G` 是 `Quantity(Fraction(1, 10**16), Unit.G)`。`TO_TASTE` 是 F01 的。
- “代码目录”是 2.5 的示例在代码里构建的目录：`tests/data/example/catalog.toml` 的六个分类和 22 种食材，按它的顺序，没有标签。“代码常备清单”是那个示例的常备清单：食用油、盐、糖、生抽和花椒。“空常备清单”是 `Pantry(frozenset())`。“代码菜谱”是那个示例的八个菜谱：示例文件夹的七个和 `scallion-noodles`，每个都是 2 份，按示例的顺序放在一个 `dict` 里。
- 在用例里，代码字体的中文名称，比如 `番茄`，是用例所用目录里这个名称的食材，即 `catalog.find_ingredient("番茄")` 给出的那个。分类的键，比如 `produce`，是目录里这个键的分类。
- `R(three, 3: 番茄 100 g, 鸡蛋 1)` 是 `tests/f12_support.py` 的 `recipe` 像 2.5 的示例那样构建的菜谱：`Recipe("three", BiText("three"), 3, (), lines, Steps(("Cook.",)))`。每一行是这个中文名称的食材，以及 `parse_quantity` 用这种食材的默认单位从其余文字读出的数量。不写数字的 `R(r1: ...)` 是 2 份。用例的映射是一个 `dict`，从每个菜谱的 ID 对应到这个菜谱。
- 一道菜写成它的菜谱 ID 和份数，所以 `tomato-egg 2` 是 `Dish("tomato-egg", 2)`。菜单写成它的周、餐次和有菜的餐位，比如“周一晚餐：`r1 2` 和 `r2 2`”。`tests/f06_support.py` 的 `make_menu` 构建它，其他每个餐位都没有菜。除非用例另有说明，周是 2026-W48，餐次是午餐和晚餐，目录是代码目录，常备清单是空常备清单。
- `build` 代表 `build_shopping_list(menu, mapping, catalog, pantry)`。
- `番茄: 600 G` 代表 `ShoppingLine(番茄, (600 G,))`，`葱: 5 STALK, 1 BUNCH` 代表 `ShoppingLine(葱, (5 STALK, 1 BUNCH))`，`白胡椒粉: ()` 代表 `ShoppingLine(白胡椒粉, ())`。`produce [番茄: 600 G, 葱: 5 STALK]` 代表 `ShoppingGroup(produce, (番茄: 600 G, 葱: 5 STALK))`。在一个分组里，每一行从一个食材名称和它的冒号开始，冒号后面的数量属于这一行。
- `List(2026-W48, 1, 2, [g1, g2], [食用油, 盐])` 代表 `ShoppingList(IsoWeek(2026, 48), 1, 2, (g1, g2), (食用油, 盐))`。预期的清单用 `==` 和结果比较。
- EN 和 ZH 是 `Lang.EN` 和 `Lang.ZH`。“EN 文字：a 和 b”指清单各行按分组和行的顺序调用 `amount_text(Lang.EN)`，给出 `"a"` 和 `"b"`。
- `Category` 或 `Ingredient` 的“相等但不同的副本”是用相等的字段新建的对象，所以它与原来的对象 `==`，但不是同一个对象。
- F12-T07、F12-T28 和 F12-T33 使用 `tests/conftest.py` 的固件 `default_int_limit`，它在测试期间把 Python 对 `int` 位数的上限设为默认的 4,300 位。设计 2.2 和选择 10 说的是这个默认值下的上限。

`tests/f12_support.py` 的辅助函数如下：

- `code_catalog()` 给出代码目录。`code_pantry(catalog, names)` 给出由这些中文名称的食材组成的常备清单，不传 `names` 时给出代码常备清单。
- `recipe(catalog, recipe_id, lines, servings=2)` 构建 `R`。`code_recipes(catalog)` 给出代码菜谱。
- `line(catalog, name, *amounts)` 和 `group(catalog, key, *lines)` 用目录里的条目为预期的清单构建 `ShoppingLine` 和 `ShoppingGroup`。`expected_w47(catalog)`、`expected_s16(catalog)` 和 `expected_s18(catalog)` 用一个目录的条目给出 F12-T29、F12-T30 和 F12-T31 预期的清单。
- `written(shopping, lang)` 写出每个分组的 `category.name.get(lang)`，并把每一行写成 `- `、食材的 `name.get(lang)`、一个空格和 `amount_text(lang)`，与 2.5 的示例一样。
- `read_week(folder, week)` 读取 F13 的 `shop` 将来要读的文件（设计第 2 节）：`read_settings`、`list_recipe_ids`、用设置和这些 ID 调用 `read_week_menu`、`read_catalog`、用目录调用 `read_pantry`，再对菜用到的每个 ID 调用一次 `read_recipe`，按菜第一次用到它们的顺序放进一个 `dict`。它检查每个读取函数都给出值、没有错误，并给出菜单、映射、目录和常备清单。
- `s16_folder(example, target)` 和 `s18_changes(folder)` 写出 v0.1-S16 和 v0.1-S18 的文件（F12-T30 和 F12-T31）。

## 3. 性能用例

无。F12 的接口都没有性能指标（设计 2.1 到 2.5，选择 11），R14 只给有性能指标的接口性能测试。PT01 在 Troy 的电脑上为 F13 的 `shop` 从启动到退出计时（v0.1-S32）。`shop` 调用一次 `build_shopping_list`，所以 F13 为 `shop` 设的性能用例会把这次调用作为命令的一部分计时。

因此这份方案把计时留给 F13。架构师的模型在 `tests/pt01_support.py` 的 PT01 周 2026-W26 上，`build_shopping_list` 的中位数是 5.1 毫秒，`amount_text` 用两种语言写出它的 290 行用了 1.9 毫秒（设计第 4 节）。这不到 PT01 那 1 秒的 1%，单独给这个函数计时的用例也没有可以判定失败的指标。F12-T23 和 F12-T28 构建 21 餐、63 道菜的星期，这是一个 PT01 周最多的菜数，但不计时。
