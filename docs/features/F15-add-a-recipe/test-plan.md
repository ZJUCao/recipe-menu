# F15 Add a recipe: test plan

## 1. Feature

- ID and name: F15 Add a recipe
- Design: [design.md](design.md), version 1.1

## 2. Cases

The tests call `ADD_COMMAND` of `recipe_menu.commands.add`, `check_recipe` and `problem_block` of `recipe_menu.commands.check`, `Context` of `recipe_menu.app`, `use_utf8_input` of `recipe_menu.text`, `main` of `recipe_menu.cli`, and `python -m recipe_menu`. A unit case calls `ADD_COMMAND.run`, `Context`, `main` with a stand-in command, `use_utf8_input`, `check_recipe`, or `problem_block` with values that it builds. A functional case runs `main` with a command line and a stream of answers, as you type `recipe-menu add` and answer its questions. It passes no `commands`, so `main` uses the real `COMMANDS`, which holds `ADD_COMMAND` after `SEARCH_COMMAND` from the mock PR on (design choice 1). An integration case runs a v0.2 scenario at `main`, starts `python -m recipe_menu add` with its answers on a pipe, builds random answers, or runs on the PT01 data folder. To know what a saved file must read back as, a case also calls `read_catalog`, `Catalog.find_ingredient`, and `Catalog.find_tag` of `recipe_menu.catalog`, `read_recipe` of `recipe_menu.recipes`, and `parse_quantity` of `recipe_menu.units`, as their designs give them. No case is a performance case (section 3). Each case names the part of the design that it comes from, such as (choice 9). The design's seven examples and their one `# raises` line are in F15-T01 (2.1), F15-T03 (3.1 and 3.2), F15-T04 (3.3), F15-T05 (3.4), F15-T06 (3.5), and F15-T07 (2.2).

**Points A to C.** Troy approved design 1.0 on 2026-11-20 with the recommendation of each point: the 32 messages of 2.2 as written (A), either language of the name, and either list of steps, may stay empty when the other language has text, and the check after saving warns about the gap (B), and the line of `add` right after the line of `search` in the help (C). Design 1.1 changes none of the three. The cases check each message of point A in both languages:

- `ADD_HELP`: F15-T01.
- The prompts of questions 1 to 7 and `EN_STEPS_OPTIONAL_PROMPT`: F15-T07 and F15-T08 in Chinese, and F15-T07 and F15-T25 in English. `EN_STEPS_PROMPT`: F15-T15, in both languages. `SERVINGS_PROMPT` with servings other than 2: F15-T02.
- `NOT_AN_ID`: F15-T10. `ID_EXISTS`: F15-T09. `NAME_NEEDED`: F15-T11. `SERVINGS_WRONG`: F15-T12. `UNKNOWN_TAG` in both its forms and `NO_TAGS`: F15-T13. `NAME_AND_QUANTITY`, `UNKNOWN_INGREDIENT`, and the four amount messages: F15-T14. `STEPS_NEEDED`: F15-T15. Each in both languages.
- `SAVED`: F15-T08 in Chinese and F15-T25 in English. `SAVED_WITH_PROBLEMS`, `ERROR_COUNT` and `WARNING_COUNT` in both their forms, and `FIX_AND_CHECK`: F15-T11, F15-T15, and F15-T23, in both languages.
- `INPUT_ENDED`: F15-T17. `APPEARED`: F15-T21. `NOTHING_SAVED` and `LEFT_BEHIND`: F15-T22. Each in both languages.

Point B is in F15-T07, F15-T11, F15-T15, F15-T23, and F15-T28. Point C is in F15-T01 and in the change to F11-T01 below.

**R09.** The mock defines every message and `ADD_COMMAND` with all its fields, and adds the entry to `COMMANDS`. It adds the field `input` with its default to `Context`, and the parameter `stdin` to `main`, which it does not pass on. Its `use_utf8_input` changes nothing, its `check_recipe` and `problem_block` give `()`, and its `run` reads no file, reads no answer, writes nothing, and gives 0 (design section 2). So a test passes against the mock when it checks only the fields of `ADD_COMMAND`, the help, a message, exit code 0, an empty error stream, the default of `Context.input`, the equality of contexts, `check_recipe` of a clean recipe, `problem_block` of no problems, or that a run writes no file or reads no answer. The same holds for what `cli` does before it runs `add`: a missing data folder, broken settings, an extra word, an unknown option, a wrong global option, and `add --help`. Each case that checks such a thing also checks something that the mock gets wrong: the output of `add`, which always starts with a prompt, exit code 1 or 130 from it, the bytes of a new file, the lines of a stop or a failure, the stream that `main` passes on, the encoding and the line ends that `use_utf8_input` sets, or the problems and lines that `check_recipe` and `problem_block` give. F15-T01, F15-T03, F15-T05, F15-T06, F15-T09, F15-T19, and F15-T24 check such things only beside a result that the mock gets wrong. Every case that expects exit code 0 from `add` also checks its output or its file, which the mock never gives. Most of their lines ask for the whole output, which is never empty. These ask for less. The second and third runs of the example of 2.2 in F15-T07, F15-T12 line 3, F15-T16 lines 1 and 3, and F15-T28 ask for the lines that they name, such as `SAVED` as the last line, and for the file. F15-T17 line 7 asks for the text of the output at each read and for the file, and F15-T16 line 4 asks only for the file. Each still fails against the mock, which writes no line and no file. `tests/f15_support.py` and `tests/f15_texts.py` call no interface of F15 when they are imported.

**Both systems.** Every case runs on Linux and on Windows, and no case is skipped on either. CI runs only on Linux, and only Troy's PC runs the tests on Windows. A problem names its file relative to the data folder, with the system's separator. So in an expected line, `recipes/new-dish.toml` stands for `str(Path("recipes", "new-dish.toml"))`: `recipes\new-dish.toml` on Windows, as the F15 prototype shows paths, and `recipes/new-dish.toml` on Linux. `SAVED`, `SAVED_WITH_PROBLEMS`, `APPEARED`, and `LEFT_BEHIND` name a file by its full path (choice 11). A path that starts with the folder of a case, such as `F/recipes/new-dish.toml`, stands for `str` of that full path. `add` writes UTF-8 with LF line ends on both systems (choice 10). No case needs an entry that one system cannot make. The names that differ from an ID only in case, such as `New-Dish.toml`, and the names that are not recipe IDs, such as `Rice Bowl.toml`, are valid file names on both systems, and no case makes a file named after a Windows device. So no F15 case joins F04-T12, F04-T51, F06-T28, and F11-T11, which run only on Linux.

F15-T03 and F15-T04 build each wrapper that stands for the standard input with `newline="\n"`, as Python builds `sys.stdin` on Linux and macOS (design 3.3). A wrapper with the default `newline`, which is `None`, already ends a line at CR LF and at a lone CR on every system, and so does `sys.stdin` on Windows. Such a wrapper would pass with or without the `newline=None` of the call. So the two cases see the line ends that `use_utf8_input` sets in the same way on both systems. F15-T27 sees them through the real standard input on Linux, where it ends a line only at LF until `use_utf8_input` changes it.

**Access that is denied.** No case denies access through the file system, with `os.chmod`, an access list, or `listing_denied` of `tests/f04_support.py`. The root user on Linux ignores the mode bits, so a test that relies on them fails as root. Every `PermissionError` in the cases comes from the fault harness, which raises it the same way for every user. So every case passes as root on Linux and as an administrator on Windows.

**How a case makes the disk fail.** The cases use `shop_faults(base, *rules)` of `tests/f13_support.py`, with the rules and the effects of the F13 and F14 test plans: `open P: E` and `open P: race` for the open of P in mode `x`, `write P: E`, `close P: E`, `unlink P: E`, `read P: E`, and `read P: later E`, and the effects `DENIED`, `IO`, `NO_SPACE`, and `CTRL_C`. So `open recipes/new-dish.toml: race` creates the file with `b"mine\n"` just before the open of `create_file`, as another program would. `read catalog.toml: later DENIED` lets step 1 of 2.2 read the catalog and makes the read of `check_recipe` fail. A case that raises `KeyboardInterrupt` gets it back as exit code 130 from `main` through `add` of `tests/f15_support.py`. That helper turns a `KeyboardInterrupt` that leaves `main` into a failure, as `call_main` of `tests/f08_support.py` does.

The note for the Developer: the cases hold only when `add` reaches the disk through `read_catalog`, `list_recipe_ids`, `create_file`, and `check_recipe` (design section 2), and these keep the calls that the F11 and F14 test plans name. A call that bypasses `io.open`, `os.scandir`, `os.listdir`, or `os.unlink`, such as `os.open` or `Path.write_text`, escapes the harness, and F15-T18, F15-T20, F15-T22, and F15-T23 fail.

**The record of the reads.** F15-T05 and F15-T20 record which files a call opens and removes and which folders it lists, with `shop_faults(F.root)` and no rule, as F14-T14 does. The harness records each open of a path under the data folder as `read`, or as `open` for mode `x`, each removal as `unlink`, and each move as `move A B`, with the paths relative to the folder and `/`. It records each listing by `os.scandir` or `os.listdir` in "the listings". `cli` reads `settings.toml` before it runs a command, so every record of a run of `main` starts with `read settings.toml`.

**The answer streams.** `tests/f15_support.py` gives these input streams. Each holds the lines of its answers A, each followed by `"\n"`:

- The plain stream of A is an `io.StringIO`, whose `isatty()` gives false.
- A terminal stream of A is the same, but its `isatty()` gives true, as a console's does.
- A watched stream has no answers and fails the case when anything reads it, with `read`, `readline`, `readlines`, or iteration. Its `isatty()` gives false.
- A hook stream of A with the change C at answer k runs C on the data folder just before it gives the k-th line of A, counted from 1, as you would in another window while `add` waits. "At its last answer" means at the last line of A.
- A stop stream of A at answer k raises `KeyboardInterrupt` in place of the k-th line, as Python's console reader does for Ctrl+C at a prompt.
- A flush record is an output stream that records its whole text at each `flush()`, and an input stream of A that records the text of that output stream at each `readline()`.

These rules hold for the test data, as in the F11, F13, and F14 test plans:

- `EXAMPLE` is the folder `tests/data/example/` of the repository (architecture 10). The fixture `example_folder` of `tests/conftest.py` copies it to `tmp_path / "recipe-menu"` with LF line ends and gives a `DataFolder` on the copy. In a case, `example` is that `DataFolder`. Its seven recipes, in ID order, are `choy-sum`, `cola-wings`, `mapo-tofu`, `red-braised-pork`, `rice`, `tomato-egg`, and `tomato-egg-noodles`. "A new example at P" is a further copy, made with `copy_example` of `tests/f05_support.py`. "A new example" with no P is at a path of its own under `tmp_path`. "A copy" in a case is a new example with the same changes.
- `home` is `tmp_path / "home"`, an empty folder that `make_home` of `tests/f05_support.py` makes.
- The tests write every file with `write` of `tests/f03_support.py`, which writes UTF-8 with LF line ends and makes its folders first, or as bytes with `put_bytes`. "X replaced by Y in F" replaces the first X in the file F with `edit` of `tests/f07_changes.py`, which checks that F holds X.
- No test changes the repository, touches `~/recipe-menu`, or reads the clock. Every call of `main` passes `home`, `environ`, and `today`. F15-T27 starts `python -m recipe_menu` through `pipe_module` of `tests/f15_support.py`. It runs as `run_module` of `tests/f05_support.py` does, with the same environment, so `HOME` and `USERPROFILE` name a folder in `tmp_path` and `PYTHONIOENCODING` is `ascii`, and it also writes the bytes of the case to the standard input of the process and closes it. It decodes stdout and stderr as UTF-8 and turns each `os.linesep` into `"\n"`, so it undoes only the CR LF that Python's text streams write on Windows. A CR that `add` writes stays in the text on both systems, also on Linux, where those streams write LF alone. A case changes the current folder only with pytest's `monkeypatch.chdir`.

These conventions hold for the calls of `main`:

- A line such as `add --lang zh` in F with A stands for `add(home, F, A, "--lang", "zh")` of `tests/f15_support.py`. It runs `main` with `["add", "--data", str(F.root), "--lang", "zh"]`, `home`, `environ={}`, `today=date(2026, 11, 10)`, two new `io.StringIO` streams, no `commands`, and `stdin` set to the plain stream of A, or to the stream that the case names. - A line of another command, such as `show garlic-broccoli` or `check`, runs through `at` of `tests/f09_support.py`. `--help` lines run through `call` of `tests/f07_support.py`.
- An answer in backticks is its text as shown, such as `快手, 素` or `a\b`. An answer in quotation marks is a Python string with its escapes, such as `""`, `" rice\t"`, or `"\u3000"`, and each `\uXXXX` or `\xXX` in it stands for that one character. "No answers" is an empty stream.
- The result is `(code, out, err)`. `(c, out L)` stands for `(c, out, "")`, where out is the lines of L, each followed by `"\n"`. `(c, out L, err M)` gives both streams in the same way, and `(c, err M)` has an empty out. Where a case gives out as a text, that text is the whole of out. The tests compare the whole texts.
- "The file" of a case is `F.recipe_file(ID)` for the ID of its answers. "The listing of `recipes/`" is the sorted names of its entries, as `os.listdir` gives them, so it shows each name exactly as the system keeps it.

## 3. Performance cases

None. No F15 interface has a performance target. PT01 names `check`, `list`, `show`, `search`, `menu show`, and `shop`, and not `add` (requirements 7.1, design section 2). So `add` gets no timed case (R14). F15-T29 runs it on the PT01 data folder without timing it, as v0.2-S16 does, and the rest of the time of `add` is your typing (choice 14).

F15 also adds to the start of every command: `cli` imports the files of `add`, and from the implementation PR on it calls `use_utf8_input(sys.stdin)` once. Choice 14 says that both take a few milliseconds. The Architect measured about 3 ms of self time for the 4 new files of its model under `python -X importtime`, 14 µs for the call, and no difference beyond noise in the start of `import recipe_menu.cli` (design section 4, note 1). In the review of design 1.1, on main with the mock, the 3 new files of `add` took 2.1 to 2.5 ms, the 4 new files with that of `check` 3.0 to 4.5 ms, and a `reconfigure` of a piped stdin with `newline=None` 14 µs. These times come from the review's sandbox, not from v0.2's release test (design section 4, note 5). `check` has 172 ms left under PT01's 1 second on Troy's PC, with a median of 0.828 s after F14. The PT01 cases of F07, F09, F10, F11, and F13 time the start of their commands in every PR, and v0.1-S27 to v0.1-S32 run again in v0.2's release test. So a slower start shows in the commands that PT01 names, and F15 needs no timed case of its own for it.
