# F01 Quantities and units: test plan

## 1. Feature

- ID and name: F01 Quantities and units
- Design: [design.md](design.md), version 1.1

## 2. Cases

The tests call the interfaces of `recipe_menu.lang` and `recipe_menu.units` directly and read no files. F01 has no command, so the plan has no functional cases. The integration cases take the quantities of the F09 and F13 prototypes through several interfaces in a row.

Each case depends on code that the mock leaves out: a method or function body, or the checks in `Quantity`. So each test fails against the mock (R09). Section 4 lists what the mock declares in full.

These conventions hold in every case:

- A string in double quotes is a Python literal, so `"　"` is the ideographic space U+3000 and `"\t"` is a tab.
- `300 G` stands for `Quantity(Fraction(300), Unit.G)`, and `3/2 KG` stands for `Quantity(Fraction(3, 2), Unit.KG)`.
- `NOT_A_NUMBER("a few")` stands for `WrongQuantity(WrongQuantityReason.NOT_A_NUMBER, "a few")`, and `UNKNOWN_UNIT("1 cups", "cups")` stands for `WrongQuantity(WrongQuantityReason.UNKNOWN_UNIT, "1 cups", "cups")`. The other reasons are written the same way.
- Each amount in a result is a `Fraction`. The test checks its type as well as its value, because `Fraction(300) == 300` is also true when the amount is the `int` 300.
- Whitespace is every character for which `str.isspace` is true, U+3000 included, as in step 1 of design 2.7.
- "At 2" means scaled by `Fraction(2, 2)`, a 2-serving recipe cooked for 2 servings. "At 4" means scaled by `Fraction(4, 2)`.
- A long text or a large amount is a Python expression, such as `"0" * 15 + "1 g"` or `Quantity(Fraction(10**4300), Unit.G)`.
- Python limits the digits of an `int` that it reads from a string or writes to one. F01-T24 and F01-T54 to F01-T57 set that limit to its default of 4,300 digits with `sys.set_int_max_str_digits(4300)`, and put the old limit back afterwards. So `PYTHONINTMAXSTRDIGITS` cannot change their results.

## 5. Alignment with the Interface Designer

| Round | Question | Answer |
| --- | --- | --- |
| 1 | Question 1, for F01-T23. Step 2 of design 2.7 accepts `to taste` "with any whitespace between the two words". Does "any whitespace" include none, so that `"totaste"` gives `TO_TASTE`? (a) No. The two words need at least one whitespace character between them, so `"totaste"` starts with a letter and is `NOT_A_NUMBER`. (b) Yes. `"totaste"` gives `TO_TASTE`. The plan recommends (a): the step speaks of two words, and no other text without a space becomes to taste. | (a). "Any whitespace" means one or more whitespace characters of any kind, and at least one, because the step speaks of two words. `"totaste"` and `"TOTASTE"` reach step 3 with an empty number and give `NOT_A_NUMBER("totaste")` and `NOT_A_NUMBER("TOTASTE")`. The design needed no change. Version 1.1 rewords step 2 to "with one or more whitespace characters between the two words" to make it clear. F01-T23 follows this answer. |
| 1 | Question 2, for F01-T24. Design 2.7 says that `parse_quantity` never raises and that a number is one or more ASCII digits, with no upper limit. Python's `int` and `Fraction` raise `ValueError` when they read a number of more than 4,300 digits, which is CPython's default limit, and `str` raises the same error when it writes such an integer. What does `parse_quantity` return for a number of 5,000 digits? (a) A `Quantity` with the exact amount, as the design reads today. Then `to_text` and `to_rounded_text` also write every digit without raising. (b) `NOT_A_NUMBER` for a number of more than 15 digits, not counting the point. Every amount that `parse_quantity` returns can then be scaled, added, and written. This changes design 2.7. (c) No case, because no recipe holds such a number. A 5,000-digit amount could then end `check` with a traceback. The plan recommends (b): a number that long is a typing mistake that `check` should report, and the limit keeps every later step far from Python's limit. | (b). Version 1.0 meant (a). But (a) would make `parse_quantity`, `to_text`, and `to_rounded_text` work around Python's limit only to accept an amount that can only be a typing mistake, and (c) breaks "never raises" and architecture 6. So the design changed: PR #7 "[docs] Limit amounts to 15 digits in the F01 design" merged design version 1.1, which the Architect reviewed and approved. Step 3 of 2.7 limits the number to 15 ASCII digits. The point does not count, and every digit counts, leading and trailing zeros included. The `NOT_A_NUMBER` row adds "or has more than 15 digits" and comes before `UNKNOWN_UNIT` and `ZERO`. 2.11 and 2.12 each add a `ValueError` for a rounded amount with more than 4,300 digits before the point, which only a wrong call reaches. 4,300 is the default of the limit in force, `sys.get_int_max_str_digits()`, and the tests use the default. F01-T22 and F01-T24 follow this answer, and F01-T54 to F01-T57 test the new `ValueError` rows. |
