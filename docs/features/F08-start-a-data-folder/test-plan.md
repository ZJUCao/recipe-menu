# F08 Start a data folder: test plan

## 1. Feature

- ID and name: F08 Start a data folder
- Design: [design.md](design.md), version 1.0

## 2. Cases

The tests call `INIT_COMMAND` of `recipe_menu.commands.init`, `CreationOutcome`, `Creation`, and `create_data_folder` of `recipe_menu.datafile`, `main` of `recipe_menu.cli`, and `python -m recipe_menu`. A unit case calls `Creation`, `create_data_folder`, or `INIT_COMMAND.run` with values that it builds. A functional case runs `main` with a command line, as you type `recipe-menu init`. It passes no `commands`, so `main` uses the real `COMMANDS`, which holds `INIT_COMMAND` and then `CHECK_COMMAND` from the mock PR on (design section 2). An integration case runs a v0.1 scenario at `main`, starts `python -m recipe_menu`, or makes random calls. Each case names the section of the design that it comes from, such as (3.2). The design's four examples and their 8 `# raises` lines are in F08-T01 (3.1), F08-T03 (3.2), F08-T14 (2.1), and F08-T15 (2.2).

**The two copies of the example texts (choice 2).** F08-T16 runs `init` in each language and compares each file that it wrote, byte for byte, with the same file of `tests/data/example/`, read as UTF-8, which gives LF line ends. The Chinese `settings.toml` is the English one with `language = "en"` replaced by `language = "zh"`. F08-T24 and F08-T26 compare the whole new folder with F07's init folder, which `make_init` builds from a copy of that example folder. No F08 test reads `docs/prototypes/example-data.md`. v0.1-S01 compares the files with that document, as the v0.1 test plan says. So a change to one copy alone fails a test.

**The init folder of F07 and the scenarios.** v0.1-S01 to v0.1-S03 and v0.1-S06 start with the folder that `init` creates. The F07 test plan stands in for that folder with "the init folder", which `make_init` of `tests/f07_changes.py` builds from a copy of the example folder. F07-T19 runs `check` on it for v0.1-S06, and F07-T20 for v0.1-S01 step 2, v0.1-S02 step 2, and v0.1-S04. F08-T24 runs the real `init` and checks that the folder it creates has the same entries and the same bytes as the folder that `make_init` builds. So every F07 case on the init folder also holds for the folder that `init` creates. F08-T24 then runs v0.1-S01 and v0.1-S06 at `main` on the folder that `init` created, with the lines that F07-T19 expects. F08-T25 runs v0.1-S02, and F08-T26 runs v0.1-S03. F08 does not repeat v0.1-S04: F07-T20 holds its `check` steps on the same bytes, and its `list` and `show` steps come with F09.

**R09.** The mock defines every message, `INIT_COMMAND` with all its fields, and `CreationOutcome` with its members, and it adds `INIT_COMMAND` to `COMMANDS`. Its `Creation` has no checks, its `create_data_folder` touches nothing and gives `Creation(CreationOutcome.CREATED)`, and its `run` writes nothing and gives 0 (design section 2). So a test that checks only the fields of `INIT_COMMAND`, the values of `CreationOutcome`, a valid `Creation`, the help, `init extra` or `init --tag`, a refused folder that keeps its entries, or a failure that leaves nothing would pass against the mock. Each case that checks such a thing also checks something that the mock gets wrong: the output of `run`, the files on the disk, the outcome or the problem of a `Creation`, an error that `Creation` or `create_data_folder` raises, an exit code other than 0, or the calls that the fault harness records. F08-T01, F08-T14, F08-T17, and F08-T21 check such things only beside a result that the mock gets wrong. `tests/f08_support.py` calls no interface of F08 and makes no `Creation` when it is imported.

**Both systems.** Every case runs on Linux and on Windows, and no case is skipped on either. CI runs only on Linux, and R09 counts a skipped test as a test that does not fail. So the two cases of choice 9, F08-T22 and F08-T23, also run on Linux, where a trailing space or dot is an ordinary character of a name. Each of them says what it expects on each system. The output names each file with the system's separator. So in an output line of a case, `recipes/tomato-egg.toml` stands for `str(Path("recipes", "tomato-egg.toml"))`, and `menus/` stands for `"menus" + os.sep`. The table of a new folder has the same widths on both systems, because `recipes/tomato-egg.toml` and `recipes\tomato-egg.toml` are both 23 columns wide. On Windows, `Path` compares without case, so a case that checks a path compares `str` of the two paths. F08-T05, F08-T08, and F08-T17 make a dangling link in a different way on each system, and F08-T05 and F08-T17 give a hidden file its attributes on Windows only. F08-T07, F08-T08, F08-T19, and F08-T22 expect a problem that depends on the error that the system raises, which differs between the systems, so each of them gets its message as "the message from the system" below says.

**How a case makes the disk fail.** Design 3.2 has a row for `FileExistsError`, `PermissionError`, and any other `OSError`, each for a folder and for a file, and it describes a failed removal and Ctrl+C. Few of these happen on demand on a real disk. The cases reach them in two ways:

- Real errors that every user gets on both systems. A name of 300 characters, which both systems reject (design 3.2, example), gives "any other `OSError`" for a folder and for a file: `ENAMETOOLONG` on Linux, and errno 22 on Troy's PC. `unreadable_name` of `tests/f05_support.py`, which is `a?b` on Windows and a name of 256 characters on Linux, gives such an error at the data folder and at a folder above it. A file, or a link that leads to no folder, at the data folder's path gives `NOT_A_FOLDER`. Such an entry above the data folder is not a missing folder, so the call's first `Path.mkdir` is of the path just below it, which raises `FileNotFoundError` on Windows, and `NotADirectoryError` below a file or `FileNotFoundError` below a link on Linux (section 5, round 1). On Windows, the names of choice 9 give `FileNotFoundError` at `recipes`.
- The fault harness, for everything else: `FileExistsError` from an entry that another program creates first, `PermissionError`, an error whose `strerror` is `None` or empty, a write that fails halfway, a removal that fails, a listing that fails, and Ctrl+C. The harness controls the system calls that design 3.2 names, during one call of `create_data_folder` or `main`, so the error comes at the step that the case picks. The next paragraph describes it.

No case denies access through the file system, with `os.chmod`, an access list, or `listing_denied` of `tests/f04_support.py`. The root user on Linux ignores the mode bits, so a test that relies on them fails as root, as the F04 tests note. A `PermissionError` from the harness is the same for every user. So every case passes as root on Linux and as an administrator on Windows.

**The fault harness.** `faults(base, *rules)` of `tests/f08_support.py` is a context manager. While it is open, it replaces `os.mkdir`, `os.rmdir`, `os.unlink`, `os.remove`, `os.scandir`, `os.listdir`, `io.open`, and `builtins.open` through pytest's `monkeypatch`, and it puts them back when it closes. In Python 3.13 and 3.14, `Path.mkdir`, `Path.rmdir`, `Path.unlink`, `Path.open`, and `Path.iterdir` call these functions, and the built-in `open` is `io.open`. Each replacement calls the original function, unless a rule names the call. A case opens the harness around the call that it tests, and around nothing else.

- The record is the list of the calls on a path under `base`, in order. Each call is written as a kind and the path relative to `base`, with `/`: `mkdir`, `rmdir`, `unlink` for `os.unlink` and `os.remove`, `open` for an open whose mode holds `x`, and `read` for any other open. A listing by `os.scandir` or `os.listdir` goes to a separate list, "the listings". Calls on other paths, and the calls that the harness makes itself, are not recorded.
- A rule names a kind, a path, and an effect, such as `mkdir R/menus: DENIED`. Its kind is a kind of the record, `write` for the first write to the file that an `open` of the path gave, or `list` for a listing.
- When the effect is an exception, such as `DENIED`, the harness raises it in place of the call, so the system does nothing.
- `race`: the harness first creates the entry itself, as another program would, with the original function: a folder for `mkdir`, and a file that holds `b"mine\n"` for `open`. Then it makes the call, which raises the system's `FileExistsError`.
- `after E`: the harness makes the call, closes the file that an `open` gave, and then raises E. So the entry exists, but the call never got it.
- For a `write` rule with the effect E, the harness writes the first half of the text of the first write, `text[: len(text) // 2]`, flushes it, and raises E. The file object that it gives for that open passes every other call to the real file, and closing it closes the real file.
- These names stand for new exceptions. `DENIED` is `PermissionError(errno.EACCES, "Permission denied")`, `IO` is `OSError(errno.EIO, "Input/output error")`, `NO_SPACE` is `OSError(errno.ENOSPC, "No space left on device")`, `CTRL_C` is `KeyboardInterrupt()`, and `BUG` is `RuntimeError("bug")`. `OSError(errno.EIO, "")` has the `strerror` `""`, and `TimeoutError()` has the `strerror` `None`.

Design 3.2 creates each folder with `Path.mkdir`, removes with `Path.unlink` and `Path.rmdir`, and opens each file in mode `"x"`. The harness relies on these calls and on no other detail of the code.

- The note for the Developer: the cases hold only when `create_data_folder` reaches the disk through the calls that design 3.2 names. It creates each folder with its own `Path.mkdir`, with no parents, opens each file with `Path.open` or `open` in mode `"x"`, removes with `Path.unlink` and `Path.rmdir`, and lists the data folder with `Path.iterdir`, `os.scandir`, or `os.listdir`. In Python 3.13.18 on Troy's PC, `Path.iterdir` calls `os.scandir`, `Path.open` calls `io.open`, and the built-in `open` is `io.open`. A call that design 3.2 does not name, such as `os.open`, `os.makedirs`, `Path.mkdir(parents=True)`, `Path.touch`, `Path.write_text`, or `shutil`, either escapes the rules of the harness or gives a record that differs from the steps, so the cases fail.

A case that raises `KeyboardInterrupt` gets it back through `pytest.raises`, or as exit code 130 from `main`. When `KeyboardInterrupt` leaves `main` instead, the case turns it into a failure, so a wrong implementation fails the case and does not stop the test run.

These rules hold for the test data:

- `EXAMPLE` is the folder `tests/data/example/` of the repository, which F08-T15 and F08-T16 read and never change. The fixture `example_folder` of `tests/conftest.py` copies it to `tmp_path / "recipe-menu"` with LF line ends and gives a `DataFolder` on the copy, which F08-T24 uses as `example`.
- `home` is `tmp_path / "home"`, an empty folder that `make_home` of `tests/f05_support.py` makes. "The default folder" is `home / "recipe-menu"`, which is missing unless the case makes it.
- `base` is an empty folder of its own under `tmp_path` for each call, such as `tmp_path / "t1"`. `R` is the data folder of a case: `base / "a" / "recipe-menu"`, where `a` is missing, unless the case says otherwise. "R exists, empty" means that R is the empty folder `base / "recipe-menu"`. In a rule or a record, `R/menus` stands for the path of `R / "menus"`, and `a` for `base / "a"`.
- The tests write every file as bytes, or with `write` of `tests/f03_support.py`, which writes UTF-8 with LF line ends and makes its folders first. So a file has the same bytes on both systems.
- "A dangling link at P" is made in this way. On Linux, the test calls `os.symlink(base / "nowhere", P)`. On Windows, it makes a new folder T, calls `_winapi.CreateJunction(str(T), str(P))`, and removes T, because a symbolic link needs a privilege that Troy's account lacks, and a junction does not. On both systems, `os.path.lexists(P)` is then true and `os.path.isdir(P)` is false.
- "Hidden" means this. On Windows, the test sets the attributes of the file with `ctypes.windll.kernel32.SetFileAttributesW`, `0x2` for hidden and `0x6` for hidden and system. On Linux, the dot at the start of `.keep` hides it, and `desktop.ini` gets no attribute.
- "The tree of X" lists each entry under X, found with `os.walk(X, followlinks=False)`, by its path relative to X, its kind (file, folder, or link), and the bytes of each file. It never follows a link. "The full record of X" also holds the `st_mtime_ns` of each entry, from `os.lstat`.
- "The message from the system for C", where C is a call such as `os.mkdir(U)`, comes from the error that the test gets when it makes C itself, before the call that it tests. The test first checks that C raises an `OSError` and creates nothing. The message is the one that the error table of 3.2 gives for the class of that error, in the column of a folder for `os.mkdir` and of a file for `open`: `FOLDER_EXISTS` or `FILE_EXISTS` for a `FileExistsError`, `FOLDER_CREATE_DENIED` or `FILE_WRITE_DENIED` for a `PermissionError`, and `FOLDER_CREATE_ERROR` or `FILE_WRITE_ERROR` for any other `OSError`, whose `reason` is the error's `strerror`, or its class name when `strerror` is `None` or empty. So both the row and the reason come from the system, and the case holds on both systems (section 5, round 1). On Troy's PC, each such call raises an error of the row "any other `OSError`". `os.mkdir` of a name of 300 characters or of `a?b` raises `OSError` with WinError 123, `The filename, directory name, or volume label syntax is incorrect`. `open` of a name of 300 characters in mode `"x"` raises `OSError` with errno 22, `Invalid argument`. `os.mkdir` below a file, below a dangling link, or below a folder whose name ends with a space raises `FileNotFoundError` with WinError 3, `The system cannot find the path specified`. On Linux, a name of 256 or more characters raises `OSError` with `ENAMETOOLONG`, `File name too long`, `os.mkdir` below a file raises `NotADirectoryError`, `Not a directory`, and `os.mkdir` below a dangling link raises `FileNotFoundError`, `No such file or directory`. The Test Manager made the Windows calls on Troy's PC with Python 3.13.18. No one has run the Linux calls for F08 yet, so CI checks the rule with whatever Linux gives.
- No test changes the repository, touches `~/recipe-menu`, or reads the clock. Every call of `main` passes `home`, `environ`, and `today`, and F08-T27 starts `python -m recipe_menu` with `HOME` and `USERPROFILE` set to a folder in `tmp_path`. A case changes the current folder only with pytest's `monkeypatch.chdir`.

These conventions hold for the direct calls of `create_data_folder`:

- `ITEMS(F)`, for a `DataFolder` F, is the folders `(F.recipes, F.menus, F.shopping)` and the files `((F.settings, "s\n"), (F.catalog, "c\n"), (F.pantry, "p\n"), (F.recipe_file("tomato-egg"), "t\n"))`, in the order of the table of the call in 2.2, with short texts. `ITEMS(R)` stands for `ITEMS(DataFolder(R))`.
- "The steps" of `ITEMS(R)`, with `a` missing, are 1. `mkdir a`, 2. `mkdir R`, 3. `mkdir R/recipes`, 4. `mkdir R/menus`, 5. `mkdir R/shopping`, 6. `open R/settings.toml`, 7. `open R/catalog.toml`, 8. `open R/pantry.toml`, and 9. `open R/recipes/tomato-egg.toml`. "The removal" of a step is `rmdir` of its folder for steps 1 to 5, and `unlink` of its file for steps 6 to 9. When R exists and is empty, the call lists R and starts at step 3. "A rule at step k" is the rule whose kind and path are those of step k.
- A problem is written as its file and its message, such as `menus: FOLDER_EXISTS`, or `.: FOLDER_CREATE_DENIED` for the file `Path(".")`. Every problem of F08 is an error with no place. The test checks `severity is Severity.ERROR`, `str(problem.file)`, `place is None`, `text(EN)`, and `text(ZH)`. `left` is compared as a tuple of `str` of its full paths, in order.

These conventions hold for the calls of `main`:

- A line such as `init --lang zh` in F stands for `call(home, ["init", "--lang", "zh", "--data", str(F)], environ)` of `tests/f07_support.py`, which runs `main` with `home`, `environ`, `today=date(2026, 11, 10)`, two new `io.StringIO` streams, and no `commands`, so `main` uses the real `COMMANDS`. A line "with no folder" has no `--data`. `environ` is `{}` unless the case gives it. `check` lines work in the same way.
- The result is `(code, out, err)`. `(c, out L)` stands for `(c, out, "")`, where out is the lines of L, each followed by `"\n"`, and nothing more. `(c, err L)` stands for `(c, "", err)`, where err is the lines of L, each followed by `"\n"`. `(130, "", "")` is an exit with nothing written.

## 5. Alignment with the Interface Designer

| 1 | A path above the data folder that holds a file or a link that leads to no folder. Step 2 of 3.2 says that, when nothing is at `folder.root`, the call "creates `folder.root` and each missing folder above it, from the top down". Is a path above the data folder that holds a file, such as `notes.txt` in `DataFolder(tmp / "notes.txt" / "recipe-menu")`, or a link that leads to no folder, a missing folder? Option A: no. A path is missing only when `os.path.lexists` is false, as the table of step 2 uses the words. The result is `FAILED` with `FOLDER_CREATE_ERROR`, the file `Path(".")`, and the system's reason. Option B: yes. A path is missing when `os.path.isdir` is false. The call then runs `Path.mkdir` on the path of the file, which raises `FileExistsError`, and the result is `FOLDER_EXISTS`, "The folder already exists.", although a file is there. A folder above the data folder is missing only when nothing is at its path, so when `os.path.lexists` is false for it. The call creates nothing at or above a file, or at or above a link that leads to no folder. Its first `Path.mkdir` is of the path just below that file or link, and the error table of 3.2 turns the error into a `FAILED` problem with the file `Path(".")`.
