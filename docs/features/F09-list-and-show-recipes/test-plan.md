# F09 List and show recipes: test plan

## 1. Feature

- ID and name: F09 List and show recipes
- Design: [design.md](design.md), version 1.0

## 2. Cases

The tests call `LIST_COMMAND` and `SHOW_COMMAND` of `recipe_menu.commands.browse`, `main` of `recipe_menu.cli`, and `python -m recipe_menu`. A unit case calls `LIST_COMMAND.run` or `SHOW_COMMAND.run` with a `Context` that it builds. A functional case runs `main` with a command line, as you type `recipe-menu list` or `recipe-menu show`. It passes no `commands`, so `main` uses the real `COMMANDS`, which holds `INIT_COMMAND`, `CHECK_COMMAND`, `LIST_COMMAND`, and `SHOW_COMMAND` from the mock PR on (design choice 1). An integration case runs a v0.1 scenario at `main`, starts `python -m recipe_menu`, or builds random folders. The two performance cases time `python -m recipe_menu list` and `show` (section 3). Each case names the section of the design that it comes from, such as (2.2). The design's four examples and their two `# raises` lines are in F09-T01 (2.1), F09-T02 (2.3), F09-T04 (2.2), and F09-T12 (2.4).

**Point A: the steps of `red-braised-pork`.** Troy chose option 1 of point A with the design on 2026-11-13. So the tests PR (PR 4) makes two changes beside the new tests, because test data and tests belong to the tests stage (R02, R08):

1. In `tests/data/example/recipes/red-braised-pork.toml`, the list `zh` of `[steps]` holds the four steps of the F09 prototype "A missing language", word for word and in this order, in place of its three steps: `五花肉冷水下锅，焯水后捞出。`, `小火把冰糖炒成焦糖色，下五花肉翻炒上色。`, `加生抽、姜片和热水，没过肉，小火炖 1 小时。`, and `大火收汁，撒上葱段。`. The rest of the file keeps its bytes, and the file still has no `en` steps.
2. In F04-T38, which is `test_f04_t38_the_other_six_example_recipes` in `tests/test_f04_example_recipes.py`, the count of Chinese steps changes from 3 to 4. Nothing else in that test changes. The F04 test plan, version 1.1, says so in its row of F04-T38.

On the Architect's model, with only the file changed, F04-T38 is the only test that fails, and with its count at 4 every test passes (design section 4). No other test reads the Chinese steps of that file (design point A). So the tests of the accepted features stay green, as R10 asks. F09-T13 expects the four steps as literals, which is what v0.1-S12 step 3 expects.

**Tests of earlier features.** Design section 3 says that the tests that run the real `COMMANDS` stay true with `list` and `show` in it: F05-T48, F05-T49, F07-T17, and F08-T14. The Architect ran every test of the branch on a model with both commands in `COMMANDS`, and all of them passed (design section 4). F09 changes none of these tests. F09-T01 checks the lines of `list` and `show` in the help of the real `COMMANDS` in a form that holds as F10 to F13 add their commands.

**R09.** The mock defines every message and both commands with all their fields, and adds them to `COMMANDS`. Its `run` functions read no file, write nothing, raise nothing, and give 0 (design section 2). So a test that checks only the fields of a command, a message, the help, exit code 0, or what `cli` does before it runs a command passes against the mock. That includes a missing data folder, broken settings, `list extra`, and `--tag` with no value, and also a check that no file changed. Each case that checks such a thing also checks something that the mock gets wrong: the output of `list` or `show`, an exit code of 1 or 2, a `UsageError` from `run`, or the reads that the harness records. F09-T01, F09-T02, F09-T19, and F09-T25 check such things only beside a result that the mock gets wrong. Every case that expects exit code 0 also checks the whole output. `tests/f09_support.py` and `tests/f09_texts.py` call no interface of F09 when they are imported.

**Both systems.** Every case runs on Linux and on Windows, and no case is skipped on either. CI runs only on Linux, and R09 counts a skipped test as a test that does not fail. A problem names its file with the system's separator. So in an expected line, `recipes/mapo-tofu.toml` stands for `str(Path("recipes", "mapo-tofu.toml"))`: `recipes\mapo-tofu.toml` on Windows, as the prototypes show, and `recipes/mapo-tofu.toml` on Linux. A file at the root, such as `catalog.toml`, and the folder `recipes` read the same on both systems. The tables of `list` and `show` hold no path, so their columns have the same widths on both systems, and in the Chinese tables each Chinese character takes two columns, as in the prototypes. Three kinds of input touch what the systems do differently, and each gives the same result on both:

- `recipes/rice.TOML` (F09-T11 and F09-T18). The case renames `rice.toml` to `rice.TOML` with `Path.rename`, which works on both systems, also on Windows, whose file names ignore case. `recipes/` then holds `rice.TOML` and no `rice.toml`, so `list_recipe_ids` gives `TOML_ENDING_NOT_SMALL` for it and no ID `rice` (F04 design 2.5). Linux could hold `rice.toml` beside `rice.TOML`, but Windows cannot, so no case makes both.
- `show Tomato-Egg` and `show con` (F09-T03 and F09-T16). Windows would open `tomato-egg.toml` for the first, and it keeps `con` for a device. `show` checks the value with `is_recipe_id` before it reads a file, so both give exit code 2 on both systems. No case makes a file named after a device, which Windows refuses (F04-T12 runs on Linux only for that reason).
- The data folder `One Drive/菜谱` of F09-T23, whose path holds a space and Chinese characters, is a valid path on both systems.

The Test Manager made the rename on Troy's PC with Python 3.13.18. The Test Manager also computed the expected texts below there, with the readers of main and a model of the two commands that follows the design.

**The record of the reads.** F09-T20 records which files `list` and `show` open and which folders they list. It uses the fault harness `faults(base)` of `tests/f08_support.py` with no rules. The harness records each open of a path under `base` as `read` and the path relative to `base`, with `/`, and each listing by `os.scandir` or `os.listdir` in "the listings" (F08 test plan, section 2). `browse` reaches the disk only through the readers of F03 and F04 (design section 2), which are on main. There, with Python 3.13.18, `read_toml` opens each file once through `open` or `io.open`, and `list_toml_files` lists a folder once through `os.scandir` or `os.listdir`. So the record depends on which readers F09 calls, and on no other code of F09. `cli` reads `settings.toml` before it runs a command, so every record starts with `read settings.toml`. The Test Manager made the records of F09-T20 with the readers of main and the model on Troy's PC.

These conventions hold for the calls of `main`:

- A line such as `list --tag 快手` in F stands for `call(home, ["list", "--tag", "快手", "--data", str(F)], environ)` of `tests/f07_support.py`. It runs `main` with `home`, `environ`, `today=date(2026, 11, 10)`, two new `io.StringIO` streams, and no `commands`, so `main` uses the real `COMMANDS`. F is a folder or the `root` of a `DataFolder`. A line "with no folder" has no `--data`. `environ` is `{}` unless the case gives it.
- The result is `(code, out, err)`. `(c, out L)` stands for `(c, out, "")`, where out is the lines of L, each followed by `"\n"`, and nothing more. `(c, err L)` stands for `(c, "", err)`, where err is the lines of L, each followed by `"\n"`. The tests compare the whole texts, never `splitlines()` of them, because `splitlines()` also splits at U+000D and U+2028, which F09-T09 must not find in an output.
- `STOP(W, M)` is the three lines of `stop_at_error` in English: W, two spaces and the English text of M, and `Run "recipe-menu check" to see every problem.`. `STOP_ZH(W, M)` is the same in Chinese: W in Chinese, two spaces and the Chinese text of M, and `运行“recipe-menu check”查看所有问题。`. W is a file, such as `catalog.toml`, or a file and a place, such as `recipes/mapo-tofu.toml, ingredient 3`, which is `recipes/mapo-tofu.toml，食材 3` in Chinese. `stopped` of `tests/f05_texts.py` builds the result.
- "Among the errors of `check`" means that `check` in the same folder and language exits with 1, and that its report holds the two lines `  W` and four spaces and the text of M under its heading of errors, as F07 design 2.2 writes an error.

**The steps of each case.**

1. Generate the folder.
2. Start the command once, untimed, and check its result as in step 3. Windows reads the 1,053 new files slowly the first time (F07 test plan, section 3), and Troy's own data folder does not pay that cost on each run.
3. Start the same command 5 times, each as a new process, with the general timed run: `sys.executable -m recipe_menu`, in `tmp_path`, with `HOME` and `USERPROFILE` set to an empty home folder and without `RECIPE_MENU_DATA`. Each run must exit with 0, give exactly the expected stdout, and give an empty stderr. A run that does not fails the case, whatever its time.
4. Take the median of the 5 times, and compare it with the limit of the system.
5. Record the 5 times, the median, and the range with `record_property`, so that the JUnit report holds them for the next comparison.

**How they run on Troy's PC.** The cases live in `tests/`, so they run in every full test run on Troy's PC, which the main session starts with the Python of the `recipe-menu` environment for each PR. In the F09 implementation PR, the main session also runs them alone, with `python -m pytest tests/test_f09_performance.py --junitxml=reports/pt01-f09.xml`, while no other test run, build, or install is going on. The PR description reports each median and range, and that run is the baseline. If `list` comes close to the limit, design choice 10 names the first step: a `[refactor]` PR that makes `Message.render` parse each template once, before the implementation PR. The release test runs v0.1-S28 and v0.1-S29 on the same machine.

**The benchmark checklist.** The cases answer the questions of `benchmark-checklist` in these ways:

- The limiter: design choice 10 and section 4 name it. `list` reads what `check` reads, without the pantry and the 52 menus, so reading the 1,000 recipe files limits it, as it limits `check` (F07 design, section 4). Its table adds about 40,000 characters, each measured with `display_width` up to three times. `show` reads one recipe, so the start of Python and the imports limit it: the model's `show` took about 0.02 s more than its `--version`. The cases do not profile, because a profiler slows the run. A `[refactor]` PR profiles.
- Tuning: each run is a new Python process with the installed package and its compiled files, with no coverage and no debugger, as Troy runs it. The untimed run of step 2 has read the files once. coverage.py measures only the test process, so `coverage run -m pytest` in CI does not slow the timed processes.
- Limits: `list` writes about 60 KB through a pipe, and the 1,053 files hold about 2 MB, which a disk reads in milliseconds. So the time measures the work of Python.
- Errors: steps 2 and 3 check the exit code, the whole stdout, and the empty stderr of each run.
- Repeatability: 5 timed runs, with the median and the range recorded. A difference from the baseline that is smaller than the range of the baseline's runs is no measurable change.
- Relevance: each case times the whole command from start to exit, which is what Troy waits for. `list` without `--tag` does the most work of `list`: `--tag` reads the same files and writes fewer rows, and the model's medians of `list --tag quick` were within 0.02 s of those of `list` (design section 4).
- The work happened: the 1,000 rows and the count line of `list` show that it read every recipe, and the 12 ingredient lines of `recipe-0500` show that `show` read that recipe.
