**两个系统。** 每个用例都在 Linux 和 Windows 上运行，没有用例在任何一个系统上跳过，所以 F16 没有用例加入只在 Linux 上运行的 F04-T12、F04-T51、F06-T28 和 F11-T11。CI 只在 Linux 上运行，只有 Troy 的电脑在 Windows 上运行测试。两个系统不同的地方，用例分别给出每个系统的预期结果：

- 一行输出用相对于数据文件夹的路径、用系统的分隔符写出菜谱文件，和问题的写法一样（选择 8）。所以在预期的行里，`recipes/mapo-tofu.toml` 代表 `str(Path("recipes", "mapo-tofu.toml"))`：在 Windows 上是 `recipes\mapo-tofu.toml`，和 F16 原型的写法一样；在 Linux 上是 `recipes/mapo-tofu.toml`。以用例的文件夹开头的路径，比如 `F/recipes/rice.toml`，代表那个完整路径的 `str`，也就是编辑器得到的路径。
- 有名字的替身在 Windows 上是批处理文件 `N.cmd`，在 Linux 上是可执行脚本 `N`，就像 `code` 在 Windows 上是 `code.cmd`（选择 4）。两者运行同一个 Python 脚本。
- 在 Windows 上，`shutil.which` 对没有文件夹部分的名称先在当前文件夹里找，除非设置了 `NoDefaultCurrentDirectoryInExePath`；在 Linux 上它从不这样做。F16-T14 的第 6 行给出每个系统的结果，并自己设置或删除这个变量，因为 Claude 的会话设置了它，而 Troy 的终端没有。
- 用 `SIGTERM` 结束自己的替身在 Linux 上给出退出码 -15，在 Windows 上给出 15，因为在那里 `os.kill` 用它得到的数字作为进程的退出码（F16-T17）。
- 真正启动失败后，`EDITOR_NOT_STARTED` 里的原因是系统自己的文字，用系统的语言，在 Windows 上可能含有字面的 `%1`（设计第 4 节，说明 2）。F16-T16 检查它周围的消息。

没有用例需要某个系统做不出的文件名。和 ID 只有大小写不同的名称，比如 `Tomato-Egg.toml`，通过给文件改名得到，所以一个文件夹里从不会有 Windows 当作同一个的两个名称。

**防护。** 没有测试启动记事本、VS Code 或任何别的真正的编辑器，也没有测试需要控制台（选择 10）。在 Troy 的电脑上，没有键 `editor` 的 `edit` 会找到真正的记事本，忘了写这个键的测试会启动它，并一直等到有人关闭它（设计第 4 节，说明 7）。所以 F16 测试文件里的每个测试都在防护之下运行。防护是 `tests/f16_support.py` 的一个 pytest 夹具，每个 F16 测试文件把它用于自己的全部测试，比如通过 `pytestmark`。防护通过 pytest 的 `monkeypatch` 把 `PATH` 设成这个测试的一个空文件夹 `tmp_path / "f16-path"`，并把当前文件夹换成另一个空文件夹 `tmp_path / "f16-cwd"`，因为在 Windows 上 `shutil.which` 先在那里找。在 Windows 上，它还把 `PATHEXT` 设成 `.COM;.EXE;.BAT;.CMD`。所以运行 `edit` 而没有这个键的测试，在 Windows 上和在 Linux 上一样得到 `EDITOR_NOT_FOUND`。需要 `PATH` 上有某个程序的用例，同样通过 `monkeypatch` 把 `PATH` 设成它那个有名字的替身所在的文件夹。防护不改 `NoDefaultCurrentDirectoryInExePath`，因为它的当前文件夹是空的。`edit` 把测试进程的环境交给编辑器，所以替身也在防护的 `PATH` 下运行，它用完整路径启动它的 Python。

**替身。** 用例在 `settings.toml` 里用完整路径指定一个替身编辑器：测试的 Python `sys.executable`（下文写作 PY），以及替身的脚本 S（选择 10）。`tests/f16_support.py` 把每个替身做在 `tmp_path` 下它自己的文件夹里，在数据文件夹、`home` 和防护的当前文件夹之外：脚本、它的动作文件（用例在每一行之前写好），以及它的运行记录。替身不打开窗口，不读控制台，能在 CI 上运行。它每次运行时：

1. 往它的文件夹里追加一条记录：它在脚本之后收到的参数列表、它的当前文件夹，以及环境变量 `F16_MARK` 的值，没有时记为无。
2. 按顺序执行它的动作。F 是它的最后一个参数，也就是 `edit` 给出的菜谱文件。
   - `sleep T`：等 T 秒。
   - `until G`：等到文件 G 存在，最多 30 秒；30 秒后 G 仍不存在时，以退出码 9 结束。
   - `replace OLD NEW`：在 F 的字节里把第一个 OLD 换成 NEW（两者都按 UTF-8），并把字节原地写回 F。F 里没有 OLD 时它以退出码 9 结束，所以用例里的错误会显示为 `EDITOR_FAILED`。
   - `copy SRC`：把文件 SRC 的字节原地写进 F。`copy SRC DEST` 把它们原地写进文件 DEST。
   - `same`：把 F 的字节写回 F，所以文件得到新的时间，文字不变。
   - `note`：在 F 末尾加一行 `# edited by the stand-in`。这是一条 TOML 注释，所以文字变了，菜谱的问题不变。
   - `delete`：删除 F。`rename NAME`：在 F 所在的文件夹里把 F 改名为 NAME。`entry NAME`：在 F 旁边写一个文件 NAME，内容是字节 `b"mine\n"`。`drop-folder`：删除 F 所在的文件夹和里面的一切。
   - `say TEXT`：把 TEXT 和一个换行写到它的标准输出。
   - `exit N`：以退出码 N 结束。`kill`：用 `os.kill(os.getpid(), signal.SIGTERM)` 结束自己。
3. 做完最后一个动作后，以退出码 0 结束。

在数据文件夹 F 里“带动作 A 的替身”，是在 F 的 `settings.toml` 末尾加上一行 `editor = '"PY" "S"'`，并把动作 A 写进替身的动作文件。“带选项 O 的替身”在 `"S"` 之后加上 O 的每个词，各放在英文双引号里，写法和设计的 `use_editor` 一样。这些路径里没有 `'`，也没有 `"`。“安静的替身”没有动作：它立即结束，什么也不改。有名字的替身 N 是它那个替身的文件夹里的一个文件，它用自己收到的参数运行 `PY S`：在 Windows 上是 `N.cmd`，只有一行 `@"PY" "S" %*`；在 Linux 上是 `N`，有两行 `#!/bin/sh` 和 `exec 'PY' 'S' "$@"`，权限为 `0o755`。“N 在 PATH 上”把 `PATH` 设成只有那个文件夹。“替身用 W 运行了一次”指它的记录里从这一行开始有一次运行，参数是列表 W。“替身没有运行”指记录里没有运行。在第一行里，PY 代表设置里写的程序，也就是 `sys.executable` 的文字。

**时间。** 立即结束的替身所用的时间就是 Python 启动的时间。测试经理在 Troy 的电脑上测得这需要 21 到 30 毫秒，所以这样的替身比 D 点的界限早 1.9 秒以上结束，在负载很重的电脑和 CI 上也是这样。需要规则另一边的用例给替身 `sleep 2.5`。`edit` 从 `Popen` 之前一刻量到等待结束，所以那个编辑器在启动后至少 2.5 秒才结束，负载重的机器只会让时间更长。只有 F16-T18 的第 1 行等这么久。编辑器一结束，`Popen.wait(timeout=0.5)` 就返回，所以别的用例都不用等完一个半秒的步长。需要好几个步长的用例用监视的 Popen 做出它们，它立即抛出 `subprocess.TimeoutExpired`。所以 F16 测试的时间主要是启动替身的时间，加上那一次 2.5 秒的等待。

**监视的 Popen 和抛错的 Popen。** 只有用例写明时，它才通过 `monkeypatch` 替换 `subprocess.Popen`（选择 10）：

- 监视的 Popen 是真正的 `subprocess.Popen` 的子类，所以编辑器确实会启动。它记下它启动的每个进程、启动时用例输出流的文字，以及每次调用 `wait` 的超时时间和那时输出流在上一次刷新时的文字（输出流是刷新记录时）。它记下每次对 `kill`、`terminate` 和 `send_signal` 的调用，并把调用传下去。用例可以让第 k 次调用 `wait` 立即抛出 `subprocess.TimeoutExpired` 或 `KeyboardInterrupt`，不等待。其他每次调用都和真正的调用一样等待。
- 带错误 E 的抛错的 Popen 记下它唯一一次调用的参数，然后抛出 E。

**流。** `edit` 的一行把 `tests/f15_support.py` 的受监视的流作为 `stdin` 传入，除非用例指明别的流，所以只要 `edit` 在选择 6 的提示之外读取标准输入，用例就失败。别的流和 F15 测试方案里的相同：各行为 L 的普通流、L 的终端流、在第 k 行做修改 C 的 L 的钩子流、在第 k 行停下的 L 的停止流，以及 L 的刷新记录。“输入 `""`”是没有行的普通流，第一次读取就到达它的结尾。

**读取的记录。** F16-T18 和 F16-T23 用不带规则的 `tests/f13_support.py` 的 `shop_faults(F.root)` 记录一次调用打开了哪些文件、列出了哪些文件夹，和 F15 测试方案一样。故障工具把数据文件夹下某个路径的每次打开记为 `read`，路径相对于该文件夹，用 `/` 分隔；把每次用 `os.scandir` 或 `os.listdir` 的列举记在“列举记录”里。`cli` 在运行命令之前读取 `settings.toml`，所以 `main` 每次运行的记录都以 `read settings.toml` 开头。替身在它自己的进程里运行，所以故障工具不记录它的任何读写。F16 没有用例给故障工具设置规则。

给开发者的说明：只有当 `edit` 通过 `list_recipe_ids`、`read_file_text` 和 `check_recipe` 访问数据文件夹（设计第 2 节），它们保持 F14 和 F15 测试方案写明的那些调用，并且 `edit` 把 `subprocess.Popen` 和 `shutil.which` 作为它们模块的属性来调用时（选择 4），这些用例才成立。绕过 `io.open`、`os.scandir` 或 `os.listdir` 的调用会逃过故障工具，F16-T18 和 F16-T23 就会失败。`from subprocess import Popen` 这样的导入会逃过 `monkeypatch`，F16-T15、F16-T16、F16-T18、F16-T20 和 F16-T23 就会失败。

## 3. 性能用例

无。F16 的接口都没有性能指标。PT01 提到的是 `check`、`list`、`show`、`search`、`menu show` 和 `shop`，没有 `edit`（需求 7.1，设计第 2 节）。所以 `edit` 没有计时的用例（R14）。F16-T29 在 PT01 数据文件夹上运行它而不计时，和 v0.2-S16 一样。`edit` 其余的时间是你在编辑器里的时间（选择 12）。

F16 还给每个命令的启动加了一点东西：`cli` 导入 `edit` 的文件，`read_settings` 多读一个键。`edit` 只在启动编辑器的函数里导入 `subprocess` 和 `shutil`（选择 4）。架构师用 `python -X importtime` 测得它的模型的五个新文件自身用了 3.2 到 3.3 毫秒，并发现函数里的导入让每个别的命令的启动少花 11 到 15 毫秒。在 Troy 的电脑上，PT01 下的 `check` 会从 0.858 秒变成约 0.861 秒。这些时间来自评审的沙箱，不是 v0.2 的发布测试（设计第 4 节）。F07、F09、F10、F11 和 F13 的 PT01 用例在每个 PR 里给它们命令的启动计时，v0.1-S27 到 v0.1-S32 在 v0.2 的发布测试里再运行一次。所以启动变慢会在 PT01 提到的命令里显出来，F16 不需要为此单独计时的用例。

## 4. 不测的内容

| 内容 | 原因 |
| --- | --- |
| `edit` 要多长时间，F16 给每个命令启动加的时间，以及只有 `edit` 加载 `subprocess` 和 `shutil`。 | 没有性能指标提到 `edit`（R14）。架构师测过启动时间（设计第 4 节），F07、F09、F10、F11 和 F13 的 PT01 用例在每个 PR 里给它们命令的启动计时（第 3 节）。F16-T29 在 PT01 数据文件夹上运行 `edit` 而不计时。 |
| 记事本、VS Code 或任何别的真正的编辑器，`shutil.which` 在 Windows 上找到的真正的 `notepad.exe`，以及记事本把文件交给已经打开的窗口。 | 没有测试启动真正的编辑器（选择 10）。它会一直等到有人关闭编辑器，而 CI 既没有记事本也没有控制台。替身走真正的编辑器可能走的每一条路：立即结束（有修改或没有修改）、很晚才结束、失败、删除或改名文件，或者把修改留给你在提示处做（F16-T17 到 F16-T21）。v0.2-S19 让 Troy 运行记事本。 |
| 在控制台里真正按下的 Ctrl+C，之后 `Popen.wait` 给编辑器的四分之一秒，以及 `cmd.exe` 问要不要终止批处理作业。 | 没有 CI 机器有控制台，测试工具也无法在控制台里按键（设计第 4 节）。F16-T20 在 Python 为 Ctrl+C 抛出 `KeyboardInterrupt` 的地方抛出它，在等待时和在提示处读取时，并检查编辑器继续运行。那段宽限时间和那个提问来自 Python 和 `cmd.exe`，不来自 `edit`（设计第 4 节，说明 3）。 |
| 真正启动失败后 `EDITOR_NOT_STARTED` 里系统的文字。 | 它随系统和 Windows 的语言而不同，可能含有字面的 `%1`（设计第 4 节，说明 2）。F16-T16 检查它周围的消息；对用例给出 `strerror` 的错误，检查完整的一行。 |
| 路径含有 `%`、`&`、`^`、`\|`、`<` 或 `>` 的数据文件夹，加上一个批处理文件作为编辑器。 | `cmd.exe` 按它自己的规则读取批处理文件的参数，可能展开或截断这样的路径（选择 4，设计第 4 节，说明 6）。`edit` 把路径照原样作为一个参数传入，F16-T15 用 Python 编辑器和含 `&`、`^` 和 `%PATH%` 的路径，以及批处理编辑器和含空格和汉字的路径，检查了这一点。`cmd.exe` 的做法不是 `edit` 的结果，只在 Windows 上发生，数据文件夹也是 Troy 自己选的。ID 里从不会有这些字符。 |
| 在控制台里运行、盖住第一行的编辑器。 | 编辑器得到控制台（选择 4），而没有 CI 机器有控制台。F16-T15 检查编辑器得到的是进程的标准输出，而不是 `context.out`。 |
| 10 位数的退出码，比如 Windows 上程序崩溃时的退出码。 | 没有替身能在两个系统上不崩溃就以这样的退出码结束。`EDITOR_FAILED` 照 `Popen` 给出的样子显示退出码，F16-T17 检查一个由系统给出的退出码：Linux 上是 -15，Windows 上是 15（选择 11）。 |
| `edit` 等你按 Enter 时，真正的另一个程序修改菜谱。 | 没有测试能让另一个程序卡准某一步。钩子流在提示处读取时做修改，就像你在记事本的窗口里做的那样（F16-T19 的第 7 行和第 8 行）。 |
| 发布测试里的 v0.2-S12 到 v0.2-S16 和 v0.2-S19。 | 它们是 `version-tests/` 里的版本测试，由版本测试 PR 添加（TE5），或者由 Troy 运行。F16-T25 到 F16-T27 和 F16-T29 在 `main` 上运行 `edit` 的那些步骤。 |
| mock PR 之后真实运行里 F05 原型的两份帮助。 | 从 mock PR 起，真正的帮助有 `edit` 那一行。产品经理在 F16 验收时把这一行加进 F05 原型的两个帮助代码块（设计第 3 节）。 |
| F05 设计 2.3 的示例，它写 `editor = 1`，预期 `UNKNOWN_KEY`。 | F16 之后，这一行在 `editor` 处给出 `NOT_A_TEXT`（F16-T04）。没有测试运行示例里的这一行，因为 F05-T11 写的是 `colour = 1`。它的措辞留给之后的 `[docs]` PR（设计第 4 节，说明 8）。 |
