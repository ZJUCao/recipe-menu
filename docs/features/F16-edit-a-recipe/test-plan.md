# F16 Edit a recipe: test plan

## 1. Feature

- ID and name: F16 Edit a recipe
- Design: [design.md](design.md), version 1.0

## 2. Cases

The tests call `EDIT_COMMAND` of `recipe_menu.commands.edit`, `Settings` and `read_settings` of `recipe_menu.settings`, `Context` and `Arguments` of `recipe_menu.app`, `main` of `recipe_menu.cli`, and `python -m recipe_menu`. A unit case calls `EDIT_COMMAND.run`, `Settings`, or `read_settings` with values that it builds. A functional case runs `main` with a command line, as you type `recipe-menu edit`. It passes no `commands`, so `main` uses the real `COMMANDS`, which holds `EDIT_COMMAND` after `ADD_COMMAND` from the mock PR on (design choice 1). An integration case runs a v0.2 scenario at `main`, starts `python -m recipe_menu edit`, builds random values of the setting `editor`, or runs on the PT01 data folder. No case is a performance case (section 3). Each case names the part of the design that it comes from, such as (choice 6). The design's four examples and their six `# raises` lines are in F16-T01 (2.1), F16-T03 (3.1), F16-T04 (3.2), and F16-T08 (2.2).

**Points A to D.** Troy approved design 1.0 on 2026-11-21 with the recommendation of each point: the 13 new texts as 2.2 and 3.2 give them (A), a first line that names the recipe's file relative to the data folder, such as `recipes\mapo-tofu.toml` (B), an `edit` that finds the editor with `shutil.which` and starts it itself with `subprocess.Popen` (C), and, for an editor that ends with exit code 0 within 2 seconds of its start without a change to the file, the prompt `QUICK_EXIT`, one line of the standard input, and then the check (D). **The guard.** No test starts Notepad, VS Code, or any other real editor, and no test needs a console (choice 10). On Troy's PC, `edit` without the key `editor` finds the real Notepad, and a test that forgot the key would start it and wait until someone closes it (design section 4, note 7). So every test in the F16 test files runs under the guard, a pytest fixture of `tests/f16_support.py` that each F16 test file applies to all its tests, for example through `pytestmark`. Through pytest's `monkeypatch`, the guard sets `PATH` to an empty folder of the test, `tmp_path / "f16-path"`, and changes the current folder to another empty folder, `tmp_path / "f16-cwd"`, because `shutil.which` looks there first on Windows. On Windows it also sets `PATHEXT` to `.COM;.EXE;.BAT;.CMD`. So a test that runs `edit` without the key gets `EDITOR_NOT_FOUND` on Windows as on Linux. A case that needs a program on the `PATH` sets `PATH` to the folder of its named stand-in, again through `monkeypatch`. The guard leaves `NoDefaultCurrentDirectoryInExePath` as it finds it, because its current folder is empty. `edit` gives the editor the environment of the test process, so a stand-in runs under the guard's `PATH` too, and starts its Python by its full path.

**The stand-in.** The cases name a stand-in editor in `settings.toml` by full paths: the test's Python, `sys.executable`, written PY below, and the script S of the stand-in (choice 10). `tests/f16_support.py` makes each stand-in in a folder of its own under `tmp_path`, outside the data folder, `home`, and the guard's current folder: the script, the file of its actions, which the case writes before a line, and the record of its runs. A stand-in opens no window, reads no console, and runs on CI. Each run of it:

1. Appends one record to its folder: the list of the arguments that it got after its script, its current folder, and the value of the environment variable `F16_MARK`, or none.
2. Takes its actions, in order. F is its last argument, which `edit` gives as the recipe's file.
   - `sleep T`: waits T seconds.
   - `until G`: waits until the file G exists, for at most 30 seconds, and ends with exit code 9 if G is still missing.
   - `replace OLD NEW`: replaces the first OLD with NEW in the bytes of F, both in UTF-8, and writes the bytes into F in place. It ends with exit code 9 when F lacks OLD, so a mistake in a case shows as `EDITOR_FAILED`.
   - `copy SRC`: writes the bytes of the file SRC into F in place. `copy SRC DEST` writes them into the file DEST in place.
   - `same`: writes the bytes of F back into F, so the file gets a new time and keeps its text.
   - `note`: appends the line `# edited by the stand-in` to F. It is a TOML comment, so the text changes and the recipe keeps its problems.
   - `delete`: deletes F. `rename NAME`: renames F to NAME in its folder. `entry NAME`: writes the file NAME beside F with the bytes `b"mine\n"`. `drop-folder`: deletes the folder of F with everything in it.
   - `say TEXT`: writes TEXT and a line break to its standard output.
   - `exit N`: ends with exit code N. `kill`: ends itself with `os.kill(os.getpid(), signal.SIGTERM)`.
3. Ends with exit code 0 after its last action.

"The stand-in with the actions A" in a data folder F is the line `editor = '"PY" "S"'` added at the end of `settings.toml` of F, with the actions A in the stand-in's file. "The stand-in with the options O" adds each word of O after `"S"`, in double quotation marks, as the design's `use_editor` writes them. The paths hold no `'` and no `"`. "The quiet stand-in" has no actions: it ends at once and changes nothing. A named stand-in N is a file in the folder of its stand-in that runs `PY S` with its own arguments: `N.cmd` with the one line `@"PY" "S" %*` on Windows, and `N` with the lines `#!/bin/sh` and `exec 'PY' 'S' "$@"` and the mode `0o755` on Linux. "N on the PATH" sets `PATH` to that folder alone. "The stand-in ran once with W" means that its record holds one run since the start of the line, whose arguments are the list W. "The stand-in did not run" means that the record holds none. In a first line, PY stands for the program as the settings write it, which is the text of `sys.executable`.

**Time.** A stand-in that ends at once takes as long as Python takes to start. On Troy's PC the Test Manager measured 21 to 30 ms for that, so such a stand-in ends more than 1.9 seconds before the limit of point D, also on a loaded PC and on CI. A case that needs the other side of the rule gives the stand-in `sleep 2.5`. `edit` measures from just before `Popen` to the end of the wait, so that editor ends at least 2.5 seconds after its start, and a loaded machine only makes the time longer. Only F16-T18 line 1 waits that long. `Popen.wait(timeout=0.5)` returns as soon as the editor ends, so no other case waits through a half-second step. A case that needs several steps makes them with the watching Popen, which raises `subprocess.TimeoutExpired` at once. So the time of the F16 tests is mostly the start of their stand-ins and the one wait of 2.5 seconds.

**The watching Popen and the raising Popen.** A case replaces `subprocess.Popen` through `monkeypatch` only where it says so (choice 10):

- The watching Popen is a subclass of the real `subprocess.Popen`, so the editor really starts. It records each process that it starts, the text of the output stream of the case when it starts it, and for each call of `wait`, its timeout and the text of the output stream at its last flush, when that stream is a flush record. It records each call of `kill`, `terminate`, and `send_signal`, and passes the call on. A case can make the k-th call of `wait` raise `subprocess.TimeoutExpired` or `KeyboardInterrupt` at once, without waiting. Every other call waits as the real one does.
- The raising Popen with the error E records the arguments of its one call, and raises E.

**The streams.** An `edit` line passes a watched stream of `tests/f15_support.py` as `stdin` unless the case names another, so a case fails when `edit` reads the standard input anywhere but at the prompt of choice 6. The other streams are those of the F15 test plan: the plain stream of the lines L, a terminal stream of L, a hook stream of L with the change C at line k, a stop stream of L at line k, and a flush record of L. "Input `""`" is the plain stream of no lines, whose end comes at the first read.

**The record of the reads.** F16-T18 and F16-T23 record which files a call opens and which folders it lists, with `shop_faults(F.root)` of `tests/f13_support.py` and no rule, as the F15 test plan does. The harness records each open of a path under the data folder as `read`, with the path relative to the folder and `/`, and each listing by `os.scandir` or `os.listdir` in "the listings". `cli` reads `settings.toml` before it runs a command, so every record of a run of `main` starts with `read settings.toml`. A stand-in runs in a process of its own, so the harness records none of its reads and writes. No F16 case sets a rule of the harness.

The note for the Developer: the cases hold only when `edit` reaches the data folder through `list_recipe_ids`, `read_file_text`, and `check_recipe` (design section 2), which keep the calls that the F14 and F15 test plans name, and when it calls `subprocess.Popen` and `shutil.which` as attributes of their modules (choice 4). A call that bypasses `io.open`, `os.scandir`, or `os.listdir` escapes the harness, and F16-T18 and F16-T23 fail. An import such as `from subprocess import Popen` escapes `monkeypatch`, and F16-T15, F16-T16, F16-T18, F16-T20, and F16-T23 fail.

## 3. Performance cases

None. No F16 interface has a performance target. PT01 names `check`, `list`, `show`, `search`, `menu show`, and `shop`, and not `edit` (requirements 7.1, design section 2). So `edit` gets no timed case (R14). F16-T29 runs it on the PT01 data folder without timing it, as v0.2-S16 does. The rest of the time of `edit` is your time in the editor (choice 12).

F16 also adds to the start of every command: `cli` imports the files of `edit`, and `read_settings` reads one more key. `edit` imports `subprocess` and `shutil` only inside the function that starts the editor (choice 4). The Architect measured 3.2 to 3.3 ms of self time for the five new files of its model under `python -X importtime`, and found that the imports inside the function keep 11 to 15 ms out of the start of every other command. `check` would go from 0.858 s to about 0.861 s under PT01 on Troy's PC. These times come from the review's sandbox, not from v0.2's release test (design section 4). The PT01 cases of F07, F09, F10, F11, and F13 time the start of their commands in every PR, and v0.1-S27 to v0.1-S32 run again in v0.2's release test. So a slower start shows in the commands that PT01 names, and F16 needs no timed case of its own for it.
