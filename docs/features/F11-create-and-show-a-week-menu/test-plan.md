# F11 Create and show a week menu: test plan

## 1. Feature

- ID and name: F11 Create and show a week menu
- Design: [design.md](design.md), version 1.0

## 2. Cases

The tests call `MENU_NEW_COMMAND` and `MENU_SHOW_COMMAND` of `recipe_menu.commands.menu`, `NO_MENU` of `recipe_menu.menus`, `FileOutcome`, `FileCreation`, and `create_file` of `recipe_menu.datafile`, `main` of `recipe_menu.cli`, and `python -m recipe_menu`. A unit case calls `FileCreation`, `create_file`, or a command's `run` with values that it builds. A functional case runs `main` with a command line, as you type `recipe-menu menu new` or `recipe-menu menu show`. It passes no `commands`, so `main` uses the real `COMMANDS`, which holds `INIT_COMMAND`, `CHECK_COMMAND`, `LIST_COMMAND`, `SHOW_COMMAND`, `SEARCH_COMMAND`, `MENU_NEW_COMMAND`, and `MENU_SHOW_COMMAND` from the mock PR on (design choice 1). An integration case runs a v0.1 scenario at `main`, starts `python -m recipe_menu`, or builds random menus. The performance case times `python -m recipe_menu menu show` (section 3). Each case names the section of the design that it comes from, such as (2.2). The design's seven examples and their 11 `# raises` lines are in F11-T01 (2.1), F11-T02 (2.3), F11-T04 (3.1), F11-T05 (3.2), F11-T07 (3.3), F11-T15 (2.2), and F11-T26 (2.4).

**Points A to C.** Troy approved design 1.0 on 2026-11-14 with the recommendation of each point: the new texts of 2.2, 2.4, and 3.1 as written (A), English comments in a new menu file in both languages, so that `--lang zh` and `language = "zh"` change only the output (B), and option 1 of point C: the first line of every failure of `menu new` names its file or folder by its full path, also the folder `menus\` that it could not list. Architecture 4.0 and ADR-0010 record point C. The cases check each new text of point A in both languages. The English refusal is in F11-T01, F11-T15, F11-T22, and F11-T35. The Chinese lines of a new menu are in F11-T01, F11-T17, and F11-T18. The Chinese `NO_MENU` is in F11-T04 and F11-T29. The Chinese count line for one meal and one dish is in F11-T34. `NO_DISHES` is in F11-T19, F11-T20, and F11-T31 in both languages. `CHANGED_NOTHING` and `LEFT_BEHIND` are in F11-T23 in both languages. F11-T18 checks point B, and F11-T23 checks point C for a missing `menus\`, for `menus` as a file, and for a listing that fails.

**Tests of earlier features.** Design section 3 says that the tests of the real help stay true when `menu new` and `menu show` join `COMMANDS` and the second column of the help moves from 19 to 21 columns: F05-T48, F05-T49, F07-T17, F08-T14, F09-T01, F09-T19, F09-T25, F10-T01, F10-T11, F10-T15, and F10-T16. F05-T23 passes `main` its own commands, so its `INCOMPLETE_COMMAND` stays true. On the Architect's model, the whole suite of main passed: 483 tests, with the 3 cases that run only on Linux skipped on Windows (design section 4). F11 changes no test of an earlier feature and no file of `tests/data/example/`. F11-T01 checks the lines of `menu new` and `menu show` in the help of the real `COMMANDS` in a form that holds when F13 adds `shop`. With F11-T11, 4 cases run only on Linux.

**R09.** The mock defines every message, both commands with all their fields, `FileOutcome` with its members, and `NO_MENU` in `menus`, and it adds both commands to `COMMANDS`. Its `FileCreation` has the four fields without the checks of 3.2. Its `create_file` touches nothing and gives `FileCreation(FileOutcome.CREATED)`, and each `run` reads no file, writes nothing, raises nothing, and gives 0 (design section 2). So a test passes against the mock when it checks only the fields of a command, the help, a message such as `NO_MENU`, exit code 0, the values of `FileOutcome`, or the defaults and the equality of a valid `FileCreation`. The same holds for what `cli` does before it runs a command, such as a missing data folder, broken settings, `menu new 2026-W47 2026-W48`, `menu show --tag quick`, `menu show next --help`, and `recipe-menu menu`. It also holds for a check that a command changes no file, that a refused `menu new` keeps the file, or that a failure leaves nothing. Each case that checks such a thing also checks something that the mock gets wrong: the output of a command, exit code 1 or 2 from `run`, a `UsageError` from `run`, the bytes of a new file, the outcome, the problem, the `left`, or the `existing` of a `FileCreation`, an error that `FileCreation` or `create_file` raises, or the calls that the harness records. F11-T01, F11-T02, F11-T04, F11-T05, F11-T06, F11-T22, F11-T32, and F11-T35 check such things only beside a result that the mock gets wrong. Every case that expects exit code 0 from `menu show` checks the whole output, which is never empty. Every case that expects exit code 0 from `menu new` checks its three lines and the bytes of the new file. `tests/f11_support.py` and `tests/f11_texts.py` call no interface of F11 when they are imported.

**Both systems.** Every case runs on Linux and on Windows, except F11-T11, which runs only on Linux. CI runs only on Linux, so CI runs every case, and R09 counts a skipped test as a test that does not fail. A problem names its file with the system's separator. So in an expected line, `menus/2026-W47.toml` stands for `str(Path("menus", "2026-W47.toml"))`: `menus\2026-W47.toml` on Windows, as the prototypes show, and `menus/2026-W47.toml` on Linux. A path that starts with a folder of the case, such as `example/menus/2026-W48.toml` or `R/menus`, stands for `str` of that path under that folder: a full path inside `tmp_path`, with the system's separator. The tables of `menu show` hold no path, so their columns have the same widths on both systems. In the Chinese tables, each Chinese character takes two columns, as in the F11 prototype. The inputs that touch what the systems do differently each give the same result on both, or the case says what each system gives:

- One name that differs from the file's name only in case, such as `2026-w47.toml` (F11-T10, F11-T22, F11-T25, and F11-T28). Both systems can hold it, and `create_file` and `list_menu_weeks` compare the names that the listing gives, so both systems give the same result. A `WindowsPath` compares without case, so a case that checks a path compares `str` of the two paths.
- Two names in one folder that differ only in case (F11-T11). Only Linux can hold them, so the case runs only on Linux, as F04-T12, F04-T51, and F06-T28 do.
- A name that the file system folds beyond A to Z (F11-T13 input 7). NTFS treats `\u00c4.toml` and `\u00e4.toml` as one name, so the exclusive open raises `FileExistsError` on Windows, and Linux keeps the two names apart. The case expects each system's result. The Test Manager made that open on Troy's PC with Python 3.13.18, and it raised `FileExistsError`.
- A file name of 300 characters (F11-T13 input 6). Both systems reject it, with errno 22 on Troy's PC and `ENAMETOOLONG` on Linux. The case takes the message from the system, as F08-T07 does.
- A dangling link (F11-T10 and F11-T22). `dangling_link` of `tests/f08_support.py` makes a symbolic link on Linux and a junction on Windows, as in F08-T05.
- The data folder `One Drive/菜谱` of F11-T33 holds a space and Chinese characters, and it is a valid path on both systems.

**Access that is denied.** No case denies access through the file system, with `os.chmod`, an access list, or `listing_denied` of `tests/f04_support.py`. The root user on Linux ignores the mode bits, so a test that relies on them fails as root, as the F04 tests note. Every `PermissionError` in the cases comes from the fault harness, which raises it the same way for every user. So every case passes as root on Linux and as an administrator on Windows.

**How a case makes the disk fail.** The cases use the fault harness `faults(base, *rules)` of `tests/f08_support.py`, as F08 does (F08 test plan, section 2). While it is open, it replaces `os.mkdir`, `os.rmdir`, `os.unlink`, `os.remove`, `os.scandir`, `os.listdir`, `io.open`, and `builtins.open`, records each call on a path under `base`, and applies its rules. A rule is written as a kind, a path, and an effect, such as `open P: DENIED`:

- `list P: E` raises E in place of the listing of the folder P.
- `open P: E` raises E in place of the open of P in mode `x`, so the system creates nothing.
- `open P: race` first creates P with `b"mine\n"`, as another program would, and then makes the open, which raises the system's `FileExistsError`.
- `open P: after E` makes the open, closes the file, and then raises E. So P exists, but the call never got it.
- `write P: E` writes the first half of the text of the first write to the file that the open of P gave, `text[: len(text) // 2]`, flushes it, and raises E.
- `unlink P: E` raises E in place of the removal of P.
- The effects are those of the F08 test plan: `DENIED` is `PermissionError(errno.EACCES, "Permission denied")`, `IO` is `OSError(errno.EIO, "Input/output error")`, `NO_SPACE` is `OSError(errno.ENOSPC, "No space left on device")`, `CTRL_C` is `KeyboardInterrupt()`, and `BUG` is `RuntimeError("bug")`. `OSError(errno.EIO, "")` has the `strerror` `""`, and `TimeoutError()` and `OSError()` have the `strerror` `None`.

A case that raises `KeyboardInterrupt` gets it back through `pytest.raises`, or as exit code 130 from `main` through `call_main` of `tests/f08_support.py`. When `KeyboardInterrupt` leaves `main`, `call_main` turns it into a failure, so a wrong implementation fails the case and does not stop the test run.

The note for the Developer: the cases hold only when `create_file` reaches the disk through the calls that design 3.3 names. It lists `path.parent` with `Path.iterdir`, `os.scandir`, or `os.listdir`. It opens the file with `Path.open` or `open` in mode `"x"`, and writes the whole text with one call of `write` on the file object that the open gave, also when the text is empty. It removes the file with `Path.unlink`. In Python 3.13.18 on Troy's PC, `Path.iterdir` calls `os.scandir`, `Path.open` calls `io.open`, and `Path.unlink` calls `os.unlink`. A call that design 3.3 does not name, such as `os.open`, `Path.write_text`, `Path.touch`, `os.replace`, or `shutil`, escapes the rules of the harness or gives another record, so the cases fail.

**The record of the reads.** F11-T21, F11-T25, and F11-T27 record which files a command opens and which folders it lists, with `faults(F.root)` and no rule, as F09-T20 and F10-T14 do. The harness records each open of a path under the data folder as `read`, or as `open` for mode `x`, with the path relative to the folder and `/`. It records each listing by `os.scandir` or `os.listdir` in "the listings". `menu show` reaches the disk only through the readers of F03, F04, and F06, and `menu new` only through `create_file` (design section 2). `cli` reads `settings.toml` before it runs a command, so every record starts with `read settings.toml`.

The Test Manager computed the expected texts below on Troy's PC, with Python 3.13.18, the readers of main, the fault harness, and a model of both commands and `create_file` that follows the design. The model gave every output of the F11 prototype, and blocks A to F and the PT01 week of section 3 are its outputs.

These conventions hold for the calls of `main`:

- A line such as `menu show 2026-W47 --lang zh` in F stands for `at(home, F, "menu", "show", "2026-W47", "--lang", "zh")` of `tests/f09_support.py`. It adds `--data` and F, and runs `main` through `call` of `tests/f07_support.py`, with `home`, `environ`, `today=date(2026, 11, 10)`, two new `io.StringIO` streams, and no `commands`, so `main` uses the real `COMMANDS`. A line "on D" runs in the same way with `today=D`, through `on(home, F, D, *argv)` of `tests/f11_support.py`. A line "with no folder" has no `--data`. `environ` is `{}` unless the case gives it.
- A word in quotation marks is one word, written as a Python string with its escapes, such as `""`, `" this"`, or `"2026-W47\n"`. Each `\uXXXX` in a word stands for that one character.
- The result is `(code, out, err)`. `(c, out L)` stands for `(c, out, "")`, where out is the lines of L, each followed by `"\n"`, and nothing more. `(c, err L)` stands for `(c, "", err)`, where err is the lines of L, each followed by `"\n"`. `(130, "", "")` is an exit with nothing written. The tests compare the whole texts, never `splitlines()` of them, because `splitlines()` also splits at U+000D and U+2028, which F11-T30 must not find in an output.
- `STOP(W, M)` and `STOP_ZH(W, M)` are the three lines of `stop_at_error` in English and in Chinese, as the F09 test plan defines them, and `stop` of `tests/f09_texts.py` builds the result. W is a file, such as `catalog.toml`, or a file and a place, such as `menus/2026-W47.toml, Monday dinner`, which is `menus/2026-W47.toml，周一晚餐` in Chinese.
- "Among the errors of `check`" has the meaning of the F09 test plan, and `assert_among_check` of `tests/f09_support.py` checks it.

These conventions hold for the direct calls of `create_file`:

- `base` is an empty folder of its own under `tmp_path` for each call. `F` is `DataFolder(base / "recipe-menu")`, and Q is `F.menu_file("2026-W47")`. In a rule or a record, `F.menus` stands for the path of that folder, and a record names a path relative to `base`, such as `open recipe-menu/menus/2026-W47.toml`.
- A problem is written as its file and its message, such as `menus: FOLDER_MISSING`, or `.: FOLDER_MISSING` for the file `Path(".")`. Every problem of `create_file` is an error with no place. The test checks `severity is Severity.ERROR`, `str(problem.file)`, `place is None`, `text(Lang.EN)`, and `text(Lang.ZH)`. It compares `left` as a tuple of `str` of its paths, and `existing` as `str`.
- "The tree of X" and "the full record of X" are those of the F08 test plan, which `tree` and `full_record` of `tests/f08_support.py` give: each entry under X with its kind and the bytes of each file, and also the `st_mtime_ns` of each entry.

The expected texts are these. The tests write each one out as a literal in `tests/f11_texts.py`. They import no message and never read a prototype file, because the messages of `menu` and of the readers are internal (design section 2, architecture 8). `menu_text` and `EMPTY` are built by the tests.

- `SHOW_47` and `SHOW_47_ZH` are the two outputs of the F11 prototype "Show the week after you fill it", 17 lines each.
- `PROTOTYPE_FILE` is the `toml` block of the F11 prototype "Create next week's menu" as bytes: its 32 lines, each ended by LF, in UTF-8. It is the same text as the `toml` block of design 2.2.
- `menu_text(W, S)` is the file of 2.2 for the week W and the meals S, which the test builds from the rules of 2.2, as the design's example of 2.2 does: `# W: ` and the English `date_range` of W from F06, the two comments of a dish, `week = "W"`, and for each day of `Day` an empty line, `[day]`, and `meal = []` for each meal of S in the order of `Meal`. Each line ends with LF, and the text is encoded as UTF-8. S is written as a list, such as `[lunch, dinner]`.
- `NEW(P, D, M)` is the three lines of a new menu in English: `Created P for D:`, `7 days with M, all empty.`, and `Add recipe IDs to the meals, then run "recipe-menu check".`. `NEW_ZH(P, D, M)` is `已创建 P，日期为 D：`, `共 7 天，每天有M，都还是空的。`, and `在各餐里填上菜谱 ID，然后运行“recipe-menu check”。`. P is the full path of the file, D the dates in the language of the line, and M the meals as the line shows them, such as `lunch and dinner` and `午餐和晚餐`.
- `EXISTS(P)` is `P already exists. Nothing was changed.`, and `EXISTS_ZH(P)` is `P 已存在。没有做任何修改。`.
- `FAIL(Q, M)` is the three lines of a failure: Q, then two spaces and the English text of M, then `Nothing was changed.`. `FAIL_ZH(Q, M)` has the Chinese text of M and `没有做任何修改。`. `LEFT(Q, M, W)` has `menu new could not remove the file that it created. Delete it, then run "recipe-menu menu new W" again.` as its third line, and `LEFT_ZH(Q, M, W)` has `menu new 没能删除它创建的文件。请删除这个文件，然后再运行“recipe-menu menu new W”。`. Q is a full path. These are not the texts of `init`, so `tests/f11_texts.py` defines its own and does not use `fail` of `tests/f08_texts.py`.
- `NO_MENU(W)` is `There is no menu for W. Run "recipe-menu menu new W" to create it.`, and `NO_MENU_ZH(W)` is `W 没有菜单。运行“recipe-menu menu new W”创建它。`.
- `NOT_A_WEEK(V)` is `"V" is not a week. Write an ISO week such as 2026-W47, "this", or "next".`, and `NOT_A_WEEK_ZH(V)` is `“V”不是一个周。请写 2026-W47 这样的 ISO 周，或者写“this”或“next”。`, with V as typed.
- `EMPTY(W, L, S)` is the output of `menu show` for the week W with no dish, in the language L, with the meals S: `Menu for W, D` or `W 菜单，D`, an empty line, the lines of the table, an empty line, and `The menu has no dishes yet.` or `这个菜单还没有菜。`. The test lays out the table with F02's `format_table` and no `min_widths`. Its rows are the heading row, `Day` or `日期` and the heading of each meal of S, `Breakfast` or `早餐`, `Lunch` or `午餐`, and `Dinner` or `晚餐`, then one row for each date of W, with F06's `short_date` and `\u2014` for each meal. D comes from F06's `date_range`. The test first checks that `EMPTY` gives the six outputs of block F.
- `HELP` is the 21 lines of `HELP_EN_LINES` of `tests/f05_texts.py` without the line that starts with `  shop `, 20 lines in all. `HELP_ZH` is `HELP_ZH_LINES` without the line that starts with `  shop `. These are the helps of design 2.1 while `COMMANDS` holds only the seven commands of F11. Each line of the two tables has its text after 21 columns.

Blocks A to F hold the outputs of `menu show` that the cases name and that no prototype shows. Each `PS>` line gives the command line without `--data`, as the prototypes do, and runs with `--data` and the folder of its block. The output of a `PS>` line is the lines that follow it, up to and including its last line. An empty line separates it from the next `PS>` line. Each output comes with exit code 0 and an empty err. A line of a block is the body of a Python string: `\u00d7` and `\u2014` stand for one character each, as the design writes them, so the columns line up in the output and not in this document.

**Which system is Troy's PC.** CI runs only on Linux, and only Troy's PC runs the tests on Windows. So the case applies the limit of `time_limit` of `tests/pt01_support.py`: 1 second when `sys.platform == "win32"`, and 3 seconds otherwise, as F07-T25, F09-T28, and F10-T21 do. A CI job on Windows would change this plan first.

**The PT01 data folder.** `make_pt01` of `tests/pt01_support.py` writes it, as for F07-T25, F09-T28, and F10-T21, with the shape that the v0.1 test plan gives it. F11 does not change the generator. Its settings name breakfast, lunch, and dinner, with 2 servings. The menu of week k of 2026 gives the dish s of meal m on day d the recipe number `((k - 1) * 63 + 9 * d + 3 * m + s) % 1000 + 1`, counted from 0 for d, m, and s, and the first dish of each dinner has 4 servings. So `2026-W26`, from 22 to 28 June 2026, names the 63 different recipes `recipe-0576` to `recipe-0638`, three in each of its 21 meals. Any week of the folder would do, and this one is the week of the Architect's model.

**The timed run.** The case uses the general timed run of F09 in `tests/pt01_support.py`: `command_run`, `command_runs`, `record_times`, and `time_limit`, which keep their names and their behavior.

**The expected output.** `tests/pt01_support.py` gains `pt01_menu_show`, which builds the result with f-strings from the rules of the generator, and not with F02's `format_table`. The PT01 week is 26 lines. Line 1 is `Menu for 2026-W26, 22 to 28 June 2026`, line 2 is empty, and line 3 is `Day` padded to 10 columns, three spaces, `Breakfast` padded to 14, three spaces, `Lunch` padded to 14, three spaces, and `Dinner`. Then, for each day d from 0 to 6 and each line s from 0 to 2, one line: the day's cell padded to 10 columns, three spaces, the cells of breakfast and of lunch, each padded to 14 columns and followed by three spaces, and the cell of dinner. The day's cell is `Mon 22 Jun` to `Sun 28 Jun` for s equal to 0, and empty for the other lines. The cell of meal m is `Recipe NNNN \u00d7n`, where NNNN is the number `576 + 9 * d + 3 * m + s` in four digits, and n is 4 for the first dish of dinner and 2 for the others. So line 4 is `Mon 22 Jun   Recipe 0576 \u00d72   Recipe 0579 \u00d72   Recipe 0582 \u00d74`. Then an empty line and `21 meals, 63 dishes. \u00d7n: servings.`. The Test Manager compared this rule with the model's output on a PT01 folder, line for line.

**The steps of the case.**

1. Generate the folder.
2. Start the command once, untimed, and check its result as in step 3. Windows reads the 1,053 new files slowly the first time (F07 test plan, section 3), and Troy's own data folder does not pay that cost on each run.
3. Start the same command 5 times, each as a new process, with `command_runs`: `sys.executable -m recipe_menu`, in `tmp_path`, with `HOME` and `USERPROFILE` set to an empty home folder and without `RECIPE_MENU_DATA`. Each run must exit with 0, give exactly the expected stdout, and give an empty stderr. A run that does not fails the case, whatever its time.
4. Take the median of the 5 times, and compare it with the limit of the system.
5. Record the 5 times, the median, and the range with `record_property`, so that the JUnit report holds them for the next comparison.

**How it runs on Troy's PC.** The case lives in `tests/`, so it runs in every full test run on Troy's PC, which the main session starts with the Python of the `recipe-menu` environment for each PR. In the F11 implementation PR, the main session also runs it alone, with `python -m pytest tests/test_f11_performance.py --junitxml=reports/pt01-f11.xml`, while no other test run, build, or install is going on. The PR description reports the median and the range, and that run is the baseline. The release test runs v0.1-S31 on the same machine.

**The benchmark checklist.** The case answers the questions of `benchmark-checklist` in these ways:

- The limiter: design choice 11 and section 4 name it. `menu show` reads what `show` reads, plus one listing of `menus/` with 52 names, one menu file, and 62 more recipe files. So the start of Python, the imports, the catalog of 300 ingredients, and the listing of 1,000 recipe files limit it, as they limit `show`. The Architect's model took 0.03 s to 0.04 s more than `show` in the same sets. The case does not profile, because a profiler slows the run. A `[refactor]` PR profiles.
- Tuning: each run is a new Python process with the installed package and its compiled files, with no coverage and no debugger, as Troy runs it. The untimed run of step 2 has read the files once. coverage.py measures only the test process, so `coverage run -m pytest` in CI does not slow the timed processes.
- Limits: `menu show` writes about 1.5 KB through a pipe, and reads 63 recipe files, one menu file, the catalog, and the settings, about 160 KB, which a disk reads in milliseconds. So the time measures the work of Python.
- Errors: steps 2 and 3 check the exit code, the whole stdout, and the empty stderr of each run.
- Repeatability: 5 timed runs, with the median and the range recorded. A difference from the baseline that is smaller than the range of the baseline's runs is no measurable change.
- Relevance: the case times the whole command from start to exit, which is what Troy waits for. A week with three dishes in each meal of three meals, from 63 different recipes, is the most that a PT01 week holds, so `menu show` reads the most recipe files that it can read for one PT01 week.
- The work happened: the 63 cells with the names of 63 different recipes, and the count line `21 meals, 63 dishes.`, show that `menu show` read the menu and every recipe that it names.
