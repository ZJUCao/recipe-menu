# F07 Check the data files: test plan

## 1. Feature

- ID and name: F07 Check the data files
- Design: [design.md](design.md), version 1.0

## 2. Cases

The tests call `CHECK_COMMAND` of `recipe_menu.commands.check`, `main` of `recipe_menu.cli`, and `python -m recipe_menu`. A unit case calls `CHECK_COMMAND.run` with a `Context` that it builds. A functional case runs `main` with a command line, as you type `recipe-menu check`. It passes no `commands`, so `main` uses the real `COMMANDS`, which holds `CHECK_COMMAND` from the mock PR on (design section 2). An integration case runs a prototype or a v0.1 scenario at `main`, starts `python -m recipe_menu`, or mixes mistakes at random. The performance case times `python -m recipe_menu check` (section 3). Each case names the section of the design that it comes from, such as (2.2).

The Architect's review (design section 4) has five findings and a note for the next stages. The cases cover them where they touch the tests:

- Finding 1, PT01 is tight: F07-T25 times `check` on the PT01 data folder, which section 3 describes and `tests/pt01_support.py` generates. The `[refactor]` PR that the Architect recommends can time F04's readers on the same folder.
- Finding 2, the texts 没有错误。 and 没有错误，也没有警告。, which Troy approved with the design: F07-T05 and F07-T06 check them.
- Finding 3 is about the words of choice 3 and changes no behavior.
- Finding 4, a missing `recipes/`, which Troy accepted as designed: F07-T13 checks the folder's error and then one `UNKNOWN_RECIPE` for each of the 9 dishes of `2026-W47`.
- Finding 5, the F07 prototype "A syntax mistake": the next paragraph says how F07-T19 tests it.
- The note for the next stages: the paragraph on R09 below says how each case reaches code that the mock leaves out.

**The F07 prototype "A syntax mistake".** On the example folder, design 2.2 gives the lines of that section and also the warning of `recipes\red-braised-pork.toml`, which the section does not show. A fix of the prototype goes through the requirement change flow and is not decided yet. Until then, F07-T19 checks design 2.2 on two folders. On the init folder, it expects the lines of the section after its first line, with the init folder's count line, as v0.1-S06 expects. On the example folder, it expects the lines of the design's example of 2.2, with the warning. The tests write these lines as literals and never read the prototype file. So neither fix that the Product Manager can make, adding the warning to the section or giving it the init folder's count line, changes an F07 test, and v0.1-S06 holds as written.

Every case runs the `run` of `CHECK_COMMAND`, directly, through `main`, or through `python -m recipe_menu`, and checks the lines of the report. The mock's `run` reads no file and writes no report (design section 2), so each test fails against the mock (R09). The mock defines `CHECK_COMMAND` with all its fields and every message, and adds it to `COMMANDS`. So a test of the fields, the help, a usage error, or a missing data folder alone would pass against the mock, and so would a test that checks only exit code 0. F07-T01, F07-T04, F07-T17, and F07-T22 check such things only after a run whose report they check, and every case that expects exit code 0 also checks the lines of the report. `tests/f07_support.py` and `tests/pt01_support.py` call no interface of `check` when they are imported.

Every case runs on Linux and on Windows. A report names each file with the system's separator. So a file in a cell, such as `recipes/mapo-tofu.toml`, stands for `str(Path("recipes", "mapo-tofu.toml"))`: `recipes\mapo-tofu.toml` on Windows, as the prototypes show, and `recipes/mapo-tofu.toml` on Linux. A file at the root, such as `settings.toml`, and a folder, such as `recipes`, read the same on both systems. F07-T13 denies the listing of a folder with `listing_denied` of `tests/f04_support.py`, which works in a different way on each system. F07-T25 has a different time limit on each system (section 3). No case runs on one system only.

These rules hold for the test data:

- `tests/data/example/` holds the example data folder of `docs/prototypes/example-data.md` (architecture 10). The fixture `example_folder` of `tests/conftest.py` copies it to `tmp_path / "recipe-menu"` with LF line ends and gives a `DataFolder` on the copy. In a case, `example` is that `DataFolder`. "A new example" is a further copy, made with `copy_example` of `tests/f05_support.py` at a path of its own under `tmp_path`, for a case that needs more than one folder.
- "The init folder" stands in for the folder that F08's `init` creates. It is a new example without the six recipes other than `tomato-egg` and without `menus/2026-W47.toml`, with the empty folders `menus/` and `shopping/`. These are the files that v0.1-S01 expects `init` to write, byte for byte as `example-data.md` shows them.
- `home` is `tmp_path / "home"`, an empty folder that `make_home` of `tests/f05_support.py` makes. It is outside `example`, so a line with no `--data` finds no data folder unless the case puts one at `home / "recipe-menu"`. `empty` is the empty folder `tmp_path / "empty"`, and `missing` is `tmp_path / "missing"`, which does not exist.
- The tests write every file as bytes, or with `write` of `tests/f03_support.py`, which writes UTF-8 with LF line ends and makes its folders first. So a file has the same bytes on both systems. "X replaced by Y in F" replaces the first X in the file F.
- No test changes the repository, touches `~/recipe-menu`, or reads the clock. Every call of `main` passes `home`, `environ`, and `today`, and F07-T23 and F07-T25 start `python -m recipe_menu` with `HOME` and `USERPROFILE` set to a folder in `tmp_path`. F07-T13 gives back the permission of each folder whose listing it denies.

These conventions hold for the calls of `main`:

- A line such as `check --lang zh` in F stands for `main(["check", "--lang", "zh", "--data", str(F)], environ=environ, home=home, today=date(2026, 11, 10), stdout=out, stderr=err)`, where F is a folder or the `root` of a `DataFolder`. It passes no `commands`. A line "with no folder" has no `--data`. `environ` is `{}` unless the case gives it, and out and err are the texts of two new `io.StringIO` streams after the call.
- The result is `(code, out, err)`. `(c, L)` for a list of lines L stands for `(c, out, "")`, where out is the lines of L, each followed by `"\n"`, and nothing more.

These conventions hold for the expected reports:

- A problem is written as its `where` and its message, such as `recipes/mapo-tofu.toml, ingredient 3`: `UNKNOWN_INGREDIENT(name="豆瓣酱")` of a recipe. It stands for two lines: two spaces and `where`, then four spaces and the message's text. In English, `where` is the file, `, `, and the English place. In Chinese, it is the file, `，`, and the Chinese place, such as `recipes/mapo-tofu.toml，食材 3`. A problem with no place has the file alone as its `where`, such as `settings.toml` or `recipes`. The tables below give the texts of the messages and the places.
- `R(r, w, E, W)` stands for the report of 2.2 in the language of the call. `r` and `w` are the numbers of recipes and of week menus in the count line, and `E` and `W` are the lists of errors and of warnings, in order. Its lines are: the count line; an empty line; with errors, `ERRORS_HEADING` for the number of errors and the two lines of each error, and without errors, `NO_ERRORS` when there are warnings and `NO_ERRORS_OR_WARNINGS` when there are none; with warnings, an empty line, `WARNINGS_HEADING` for the number of warnings, and the two lines of each warning; with errors, an empty line and `FIX_AND_CHECK_AGAIN`. The count line is `Checked the settings, the catalog, the pantry, r recipes, and w week menus.`, with `1 recipe` and `1 week menu` for the count 1, or `已检查设置、目录、常备清单、r 个菜谱和 w 个周菜单。`. The other texts are those of the table of messages of 2.2. F07-T05 and F07-T06 write the lines of each kind of report out in full, and the helper of `tests/f07_support.py` that builds `R` follows them.
- `COUNTS` is the line `Checked the settings, the catalog, the pantry, 7 recipes, and 1 week menu.`, and `COUNTS_ZH` is `已检查设置、目录、常备清单、7 个菜谱和 1 个周菜单。`.
- `PORK` is the warning `recipes/red-braised-pork.toml, steps`: `NO_EN_STEPS`. `MAPO` is the error `recipes/mapo-tofu.toml, ingredient 3`: `UNKNOWN_INGREDIENT(name="豆瓣酱")` of a recipe. `TYPO` is the error `menus/2026-W47.toml, Monday dinner`: `UNKNOWN_RECIPE(recipe="tomato-eggs")`.
- `DISHES` is the 9 errors that `2026-W47` gives when no recipe ID is known, in this order: `UNKNOWN_RECIPE` at `menus/2026-W47.toml, Monday dinner` for `tomato-egg`, `choy-sum`, and `rice`, at `menus/2026-W47.toml, Tuesday dinner` for `mapo-tofu` and `rice`, at `menus/2026-W47.toml, Saturday lunch` for `tomato-egg-noodles`, and at `menus/2026-W47.toml, Sunday dinner` for `cola-wings`, `choy-sum`, and `rice`.
- `AFTER` is `R(7, 1, [], [PORK])` in English, the 7 lines of the F07 prototype "After the fixes": `COUNTS`, ``, `No errors.`, ``, `1 warning:`, `  recipes/red-braised-pork.toml, steps`, and `    No English steps. Commands show the Chinese steps instead.`. `AFTER_ZH` is the same report in Chinese: `COUNTS_ZH`, ``, `没有错误。`, ``, `1 个警告：`, `  recipes/red-braised-pork.toml，步骤`, and `    没有英文步骤。命令会改为显示中文步骤。`.
- `TWO` is `R(7, 1, [MAPO, TYPO], [PORK])` in English, the 13 lines of the F07 prototype "Errors and a warning, in English". `TWO_ZH` is the same report in Chinese, the 13 lines of "The same check in Chinese".
- `EMPTY` is the 15 lines of the empty folder in the design's example of 2.2, `R(0, 0, [settings.toml: FILE_MISSING, catalog.toml: FILE_MISSING, pantry.toml: FILE_MISSING, recipes: FOLDER_MISSING, menus: FOLDER_MISSING], [])` in English. `EMPTY_ZH` is the same report in Chinese, which F07-T03 writes out.
- `tests/f07_support.py` writes `AFTER`, `TWO`, `EMPTY`, and their Chinese forms out as literals, with `Path` for each file, so that these cases do not depend on the helper of `R`.

These named changes make the mistakes of the prototypes and the scenarios in a folder:

- The mapo mistake: `"郫县"` replaced by `""` in `recipes/mapo-tofu.toml`, so that ingredient 3 says 豆瓣酱, as in the design's example of 2.2.
- The typo: `"tomato-egg"` replaced by `"tomato-eggs"` in `menus/2026-W47.toml`, as `typo` of `tests/f06_support.py` writes it. The two mistakes are the mapo mistake and the typo, the mistakes of the F07 prototype.
- Pork in English: the line `en = ["Braise the pork."]` added at the end of `recipes/red-braised-pork.toml`, which removes `PORK`, as in the design's example of 2.2.
- The comma: the comma between `"盐"` and `"糖"` deleted in line 2 of `pantry.toml`, as in v0.1-S06.
- Broken settings: `settings.toml` written as the line `meals = ["lunch", "supper"]`, as in the design's example of 2.2.
- The S07 mistakes: the 9 mistakes of v0.1-S07. `  { zh = "芥兰", en = "Broccoli", category = "produce" },` and `  { zh = "香菜", en = "Coriander", category = "meats" },` added at the end of the catalog's ingredients, as ingredients 23 and 24. `"糖"` replaced by `"sesame oil"` in `pantry.toml`. In `recipes/rice.toml`, `servings = 2` replaced by `servings = 0`, `["主食"]` by `["breakfast"]`, and `"160 g"` by `"1 cups"`. The menu written by `mistakes` of `tests/f06_support.py`.
- W as a copy: `menus/W.toml` holding the example menu with `week = "2026-W47"` replaced by `week = "W"`.
- A day's key added: such as `supper = []` added to Friday, which replaces `[friday]\n` by `[friday]\nsupper = []\n` in the menu.

## 3. Performance cases

| ID | Target | Machine | Margin | Baseline |
| --- | --- | --- | --- | --- |
| F07-T25 | PT01: `recipe-menu check` finishes within 1 second with 1,000 recipes, 300 catalog ingredients, and 52 week menus. The median of 5 runs from start to exit counts. | Troy's PC: Windows 11, with Python 3.13 of the `recipe-menu` environment. The case also runs in CI, on the `ubuntu-24.04` runner of `.github/workflows/troy-mode.yml`, which is not a fixed machine (architecture 10). | On Windows, none: the median must be under 1 second, because a margin above PT01 would pass a command that misses it (v0.1 test plan, section 3). On Linux, 3 seconds, three times the target, so that the case holds on a runner of unknown speed and still fails a slowdown of several times. | First run. The Architect's model of the design took a median of 1.006 s on Troy's PC (design section 4), but a model is not the implementation. The F07 implementation PR records the first baseline. |

**Which system is Troy's PC.** CI runs only on Linux ([requirements 7](../../requirements.md#7-non-functional-requirements), `.github/workflows/troy-mode.yml`), and only Troy's PC runs the tests on Windows. So the case applies the limit of 1 second when `sys.platform == "win32"`, and the limit of 3 seconds otherwise. A CI job on Windows would change this plan first.

**The PT01 data folder.** `tests/pt01_support.py` generates it in `tmp_path / "pt01"` before the case times anything, with the shape that the v0.1 test plan gives it for v0.1-S27. So the feature case and the version test time the same kind of data. The generator writes each file with LF line ends:

- `settings.toml`: the lines `language = "en"`, `meals = ["breakfast", "lunch", "dinner"]`, and `servings = 2`.
- `catalog.toml`: the `categories` and the `tags` of the example catalog, and an `ingredients` list of 300 items. Item k, for k from 1 to 300, is `{ zh = "食材NNN", en = "Ingredient NNN", category = "C" }`, where NNN is k in three digits and C is produce, meat, eggs, staples, seasonings, or other, in turn from k = 1.
- `pantry.toml`: `pantry = ["食材291", ..., "食材300"]`, the last 10 ingredients.
- `recipes/recipe-NNNN.toml` for k from 1 to 1,000, where NNNN is k in four digits. The name is `{ zh = "菜谱NNNN", en = "Recipe NNNN" }`, and the servings are `1 + k % 4`. The tags are item `k % 5` and item `(k + 1) % 5`, counted from 0, of 快手, 家常, 素, 辣, and 主食. The 12 ingredients each have the note `{ zh = "切块", en = "cut into pieces" }`. The first is 食材001 with the amount `1 tsp`, so every recipe uses that ingredient. Then, for j from 0 to 10, comes ingredient number `2 + (11 * k + j) % 299`, with the amount `200 g`, `15 ml`, `2 个`, or `适量` for `j % 4` equal to 0, 1, 2, or 3. `[steps]` comes last, with `zh` and `en` lists of 6 steps each, such as `第 1 步：把食材洗净切好，放进锅里翻炒两分钟。` and `Step 1: Wash and cut the ingredients, and stir-fry them for two minutes.`.
- `menus/2026-WNN.toml` for each week from `2026-W01` to `2026-W52`: the line `week = "2026-WNN"`, and a table for each day from `[monday]` to `[sunday]` with the keys `breakfast`, `lunch`, and `dinner`, each a list of 3 dishes. Dish s of meal m of day d, each counted from 0, names the recipe number `((w - 1) * 63 + 9 * d + 3 * m + s) % 1000 + 1` of week w. The first dish of each dinner is written `{ recipe = "recipe-NNNN", servings = 4 }`, and the others as IDs in quotation marks. So each week has 63 dishes from 63 different recipes.
- No `shopping/`.

A recipe file is about 2 KB, and a menu file about 1.5 KB. Writing the folder takes about 0.4 s on Troy's PC, and the case does not time it. The Test Manager checked the generator in a model run on the readers of F03 to F06: the folder gives `No errors. No warnings.`.

**The steps of the case.**

1. Generate the folder.
2. Start `python -m recipe_menu check --data <pt01>` once, untimed, and check its output as in step 3. The Architect's first run took 5.3 s and the next ones about 1.0 s (design section 4). Windows reads the 1,053 new files slowly the first time, and Troy's own data folder does not pay that cost on each run.
3. Start the same command 5 times, each as a new process, as `run_module` of `tests/f05_support.py` starts it: `sys.executable -m recipe_menu`, in `tmp_path`, with `HOME` and `USERPROFILE` set to an empty home folder and without `RECIPE_MENU_DATA`. `time.perf_counter()` before `subprocess.run` and after it returns gives the time from start to exit. Each run must exit with 0 and give exactly the three stdout lines of the case and an empty stderr. A run that does not fails the case, whatever its time.
4. Take the median of the 5 times, and compare it with the limit of the system.
5. Record the 5 times, the median, and the range with `record_property`, so that the JUnit report holds them for the next comparison.
6. Untimed: add the line `fr = ["Étape 1."]` at the end of `recipes/recipe-1000.toml`, which puts the key `fr` in `[steps]`, and the line `supper = []` at the end of `menus/2026-W52.toml`, which puts the key in `[sunday]`. Run once more. These are the last recipe and the last menu that `check` reads (choice 4). The report of their two errors shows that the command read them, so the timed runs did the same work.

**How it runs on Troy's PC.** The case lives in `tests/`, so it runs in every full test run on Troy's PC, which the main session starts with the Python of the `recipe-menu` environment for each PR. In the F07 implementation PR, the main session also runs the case alone, with `python -m pytest tests/test_f07_performance.py --junitxml=reports/pt01.xml`, while no other test run, build, or install is going on. The PR description reports the median and the range. That run is the baseline. The Architect recommends a `[refactor]` PR for the readers of F04 before the implementation PR (design section 4, finding 1). It can time them on the folder of `tests/pt01_support.py`, which the tests PR adds, so that its numbers and this case's numbers come from the same data. The release test runs v0.1-S27 on the same machine.

**The benchmark checklist.** The case answers the questions of `benchmark-checklist` in these ways:

- The limiter: design section 4 names it. `read_recipe` took 0.77 s of about 1 s for the 1,000 recipes, most of it to build place texts for files with no problems. The case does not profile, because a profiler slows the run. The `[refactor]` PR profiles.
- Tuning: the case runs the command as Troy runs it. Each run is a new Python process with the installed package and its compiled files, with no coverage and no debugger, on files that the untimed run of step 2 has read once. coverage.py measures only the test process, so `coverage run -m pytest` in CI does not slow the timed processes.
- Limits: the 1,053 files hold about 2 MB, which a disk reads in milliseconds. So the time measures the work of Python on them.
- Errors: steps 2 and 3 check the exit code, the whole stdout, and the empty stderr of each run.
- Repeatability: 5 timed runs, with the median and the range recorded. A difference from the baseline that is smaller than the range of the baseline's runs is no measurable change.
- Relevance: the case times the whole command from start to exit, which is what Troy waits for.
- The work happened: the count line of each run names 1,000 recipes and 52 week menus, and step 6 shows that the command reads the last recipe and the last menu.
