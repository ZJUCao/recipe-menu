# v0.2 version test plan

## 1. Version

- Version: v0.2
- Features: F14, F15, F16
- Requirements: [docs/requirements.md](../../requirements.md#6-version-plan)

## 2. End-to-end scenarios

The scenarios follow the v0.2 flows of [requirements 3](../../requirements.md#3-how-users-interact-with-it): `menu suggest` fills the empty meals of a week, `add` asks for a new recipe one line at a time, and `edit` opens a recipe in your editor and checks it after you close the editor. They also follow the F14, F15, and F16 rows of [requirements 4](../../requirements.md#4-features) and the prototypes `docs/prototypes/F14-suggest.md`, `docs/prototypes/F15-add.md`, and `docs/prototypes/F16-edit.md`.

Claude runs a scenario as a version test in `version-tests/`. The release test runs the version tests on Troy's PC, never in CI. These rules of [the v0.1 test plan, section 2](../v0.1/test-plan.md#2-end-to-end-scenarios) hold for each of Claude's scenarios:

- Each `recipe-menu` step runs the `recipe-menu` command of the project's environment as a new process, in an empty temporary current folder, with a temporary home folder `<home>`. No scenario reads or changes `C:\Users\Troy\recipe-menu`.
- "The example folder" is a fresh copy of `tests/data/example/` at `<home>\recipe-menu`, with an empty `shopping\` folder. The Start of each scenario's steps says which folder it begins with.
- The test reads stdout and stderr as UTF-8, and counts CRLF and LF as the same line end.
- A prototype section, such as F14 "Fill an empty week", and the output of a command in it mean what they mean in the v0.1 plan. When a step "prints the output" of a section, its output equals those lines, character for character, with `<home>\recipe-menu` in place of `C:\Users\Troy\recipe-menu`.
- A message that ends a command with exit code 1 or 2 is on stderr, and any other output is on stdout.

v0.2 adds these rules:

- **The suggest folder.** The F14 prototype assumes 40 recipes, 16 of them with the tag 快手. The suggest folder is the example folder with 33 more recipes: 13 with the tag 快手, 2 with the tag 辣, and 18 with the tag 家常, one tag each. So 16 recipes have 快手, and 3 have 辣. Each new recipe makes 2 servings, has its names and steps in both languages, and uses only catalog ingredients, so `check` finds no problem in it. The settings are those of the example: lunch and dinner, and no setting for the dishes of a meal. So a week has 14 meals, and each gets 1 dish.
- **A random choice.** `menu suggest` chooses recipes at random. So a step checks what every choice must meet: the number of dishes in each meal, the tag, and no recipe twice in the week. It does not check which recipes the command chose. Only v0.2-S02 compares two choices. A correct random choice fills two weeks with the same 14 recipes in the same meals with a chance of 2 in 16!, about 1 in 10^13.
- **The rest of the file.** When a step says that the rest of a menu file stays as it was, every line outside the lists of the meals that `menu suggest` filled keeps its text and its place, comments and blank lines included.
- **Answers to `add`.** A step gives its answers on stdin, one per line, in UTF-8, and closes stdin after the last one. An empty answer is an empty line. Through a pipe, the console echoes no answer. So the step checks that stdout shows the prompts and the messages of the section in the order that the section shows them, and that its last line is the last line of the section. The F15 design gives the spaces and the line ends between them.
- **The stand-in editor.** No Claude scenario opens Notepad. An `edit` step names a stand-in editor in `settings.toml`, the way the F16 prototype names VS Code: `editor = "stand-in-editor --wait"`. The test puts the stand-in's folder on the process's PATH. There the name leads to the batch file `stand-in-editor.cmd`, as `code` leads to `code.cmd` in an install of VS Code. The stand-in records that it ran and which file it got, outside `<home>` and the current folder. It waits 1 second, makes the step's change to that file, and exits. So an `edit` that checks the recipe before the editor exits checks the old file, and its step fails.
- **The report of `add` and `edit`.** The report of the check that ends `add` or `edit` is their output. So it is on stdout with every exit code, as the report of `check` is ([architecture 6](../../architecture.md#6-error-handling)).
- **Where a prototype shows no output.** The expected result says what the output must hold, and the feature's design gives the exact words. When a design that Troy approves differs from this plan, the Test Manager updates the plan to match before the version tests PR.

**Why Troy runs three scenarios.** Claude runs every scenario that a script can run through the `recipe-menu` command. v0.2-S17 installs the tool into Troy's own uv tool folder and changes Troy's PATH, which a test must not do. Only a new PowerShell tab shows that the PATH works ([ADR-0006](../../adr/ADR-0006-install-with-uv-tool.md)). v0.2-S18 needs Troy's keyboard and Chinese input method. Claude's `add` scenarios give their answers through a pipe, so they never type into a console, never use an input method, and cannot press Ctrl+C at a prompt. v0.2-S19 needs Notepad, a window that only a person closes. Windows 11's Notepad can open a file as a tab of a window that is already open, so step 3 checks that `edit` still waits.

**What the plan leaves out.**

- Linux. CI runs the per-PR tests on Linux ([requirements 7](../../requirements.md#7-non-functional-requirements)). Claude's scenarios run only in the release test on Troy's PC, so none of them runs on Linux.
- The network. As in v0.1, a version test cannot show that a process never used the network, so no scenario checks it.
- VS Code. The F16 prototype gives `editor = "code --wait"` as an example. The stand-in editor of v0.2-S12, v0.2-S13, v0.2-S15, and v0.2-S16 is named the same way, and it is a batch file, as `code` is. The requirements do not say that Troy's PC has VS Code, so no scenario needs it.

**Where the plan waits for the designs.** Troy approved the F14 design on 2026-11-17. It settles the F14 points of the scenarios as this plan expected. The line `dishes = { dinner = 2 }` gives dinner 2 dishes (v0.2-S06). A fill without `--tag` that leaves meals empty (v0.2-S05 and v0.2-S07) and a week with no empty meal (v0.2-S03) each have their words and exit code 0, because neither is a mistake in the data. A wrong week, a missing menu, and an unknown tag give the messages and exit codes of `menu show` and `list --tag` (v0.2-S07 and v0.2-S08). A dish that you emptied can come back (v0.2-S03). A meal of 2 dishes when only 1 recipe is left stays empty, and a meal or a day that the file leaves out gets a new line or table. The F14 test plan tests both, and no scenario needs them. No design of F15 or F16 exists yet. These points of the scenarios come from their designs, and the plan changes if a design that Troy approves settles them another way:

- F15: the English prompts, the English line after saving, and the messages for wrong answers (v0.2-S10). The exit code after an empty first answer, which this plan expects to be 0 (v0.2-S11). How `add` splits `Cooking oil 2 tbsp` and `Salt to taste` into a name and a quantity, when each holds a space (v0.2-S10). That `add` reads a pipe as UTF-8, as redirected output is UTF-8 ([ADR-0004](../../adr/ADR-0004-bilingual-text.md)).
- F16: the first line when the settings name an editor (v0.2-S12), the usage message without an ID (v0.2-S13), and how the value of `editor` splits into a program and its arguments. Also how `edit` waits when Notepad opens the recipe as a tab of a window that is already open (v0.2-S19).

## 3. Performance and stress cases

None. PT01 is the only performance target ([requirements 7.1](../../requirements.md#71-performance-targets)). It names `check`, `list`, `show`, `search`, `menu show`, and `shop`, and v0.2 adds none of them. So `menu suggest`, `add`, and `edit` get no performance case (R14). v0.2-S16 runs them on the PT01 data folder without timing them, for the size that requirements 7 asks for.

**PT01 still holds in v0.2.** The six PT01 cases of v0.1, v0.1-S27 to v0.1-S32, stay in `version-tests/` and run again in v0.2's release test. Their rule stays the same: a case passes when the median of its 5 runs is under 1 second. v0.2 changes code that they time. F14 and F16 add keys to the settings that every command reads. F14 adds a random generator, and F15 an input stream, to the context that every command gets. F15 and F16 reuse `check` ([architecture 3](../../architecture.md#3-modules) and [5](../../architecture.md#5-data-model)).

The baseline is the release test of v0.1.0 on Troy's PC on 2026-11-16, as its JUnit report recorded it:

| Case | Command | Median | Range of the 5 runs |
| --- | --- | --- | --- |
| v0.1-S27 | `check` | 0.841 s | 0.832 to 3.080 s |
| v0.1-S28 | `list` | 0.782 s | 0.777 to 0.789 s |
| v0.1-S29 | `show` | 0.164 s | 0.161 to 0.174 s |
| v0.1-S30 | `search` | 0.779 s | 0.772 to 0.789 s |
| v0.1-S31 | `menu show` | 0.201 s | 0.199 to 0.202 s |
| v0.1-S32 | `shop` | 0.215 s | 0.213 to 0.219 s |

`check` used 84% of its second, and `list` and `search` used 78%. So a change to `check` or to reading recipes has little room. The release test of v0.2 records each median beside its baseline. A median more than 20% above its baseline still passes when it is under 1 second. The summary of the release test names it, so that Troy sees a slowdown before it misses PT01.
